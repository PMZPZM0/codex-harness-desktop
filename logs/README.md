# 项目日志库（`logs/`）

> 这不是"流水账目录"，是**结论档案**。流水每日记在设计好的地方（见下），这里只放**能被半年后的你检索到的东西**。

## 1 为什么要有它（为什么它重要）

三个月前为什么把 AUMID 从 dev 里删掉？那条 `if (app.isPackaged)` 看着像随手写的，删掉会怎样？
—— 这类问题的答案**不在代码里**，在当时的判断过程中。代码只留下「是什么」，「为什么」只存在于日志。

缺了它会付三种代价，本项目全都真实付过：

| 代价 | 实例 |
|---|---|
| **重复踩同一个坑** | 同一个「注释命中文案导致断言假红」的坑，09-18 记过、09-25 又踩两次 |
| **把已证伪的结论再推一遍** | 09-24 我断言「dev 也能安全设 AUMID」，09-25 A/B 实证推翻它 —— 而 09-24 的推理过程当时没留档，等于白推 |
| **返工与自我怀疑** | 「这行代码为什么长这样」查不到出处时，只能靠猜，猜错就回滚 |

⛔ **一句话判据**：如果一条信息**只存在于某次对话里**，那它等于不存在 —— 对话会被压缩、会被忘、会被下一个会话完全看不见。

## 2 与其他三处记录的关系（⛔ 别混淆，别重复记）

| 位置 | 定位 | 谁写 | 进不进上下文 |
|---|---|---|---|
| `<ws>/.workbuddy/memory/YYYY-MM-DD.md` | **每日原始流水**（宿主约定，append-only） | 每轮追加 | 否 |
| `<ws>/.codex-harness/memory/logs/` | 应用自己的 L4 层（注入用） | 捕获链自动 | 是（有预算） |
| **`<repo>/logs/`（本目录）** | **规范结论档案 + 索引**（进 git、可校验） | 人/agent 显式建条目 | 否（按需检索） |
| `<ws>/.codex-harness/memory/lessons/` | 纪律与坑（注入最前） | 捕获链 + 引擎 | 是 |

**分工一句话**：流水记「今天干了什么」，`lessons` 记「以后要遵守什么」，**本目录记「为什么这么定」**。

### ⛔⛔ 不许重复写（用户 2026-09-25：「确保没有重复写日志哈」）

三个位置**服务于不同读者**，同一内容**只在一个地方写全**，其他地方只留**指针**：

| 内容形态 | 写在哪 | 其他位置怎么写 |
|---|---|---|
| 时间线、做到哪一步、当时的零散判断 | 日报（`.workbuddy/memory/YYYY-MM-DD.md`） | —— |
| **结论 / 依据 / 影响面 / 回滚**（可被半年后检索） | **本目录条目** | 日报里**不要复述正文**，只留一行 `→ logs/<id>` |
| 一条要每轮被模型看见的纪律 | `lessons/*.md` | 需要解释来龙去脉时，在本目录建一个 `decision` 条目**指向它**，纪律本身仍留在 `lessons/` |

**判据**：同一段正文**只允许存在一份**。发现两处都在复述 ⇒ 保留信息更全的那份，另一份改成指针。

**机制层已内建两道拦阻**（不靠自觉）：

1. **写入时拦**：`new` 会比对全库 —— 标题相似度 ≥0.75 或正文哈希完全相同就**拒绝写入**并提示处理方式
   （同一件事 → 改那条或 `--supersedes`；真是两件事 → 换可区分的标题，或显式 `--allow-similar`）
2. **随时可查**：`node scripts/logs.mjs dedupe` 全库查重（内容完全相同 / 同天同类型标题相似 / 跨天相似），
   只报告不自动删 —— 留哪条、合哪条只有带上下文的人能判断


## 3 什么时候必须写（写入要求）

**必须**建条目（否则视为这次工作没做完）：

1. **定了一个方案**，尤其是"在几个可行方案里选了 A" ⇒ `kind: decision`
2. **修了一个 bug**，且根因不是显而易见的（有误判、有反直觉证据） ⇒ `kind: incident`
3. **发版 / 完成一个里程碑** ⇒ `kind: milestone`
4. **改了行为语义**（用户能感知的交互、默认值、权限边界变了） ⇒ `kind: change`
5. **推翻了以前的结论**（包括推翻自己） ⇒ `kind: decision`，并在 `supersedes` 里写旧 id

**不必**写：纯格式调整、依赖升级、重命名、一次就懂的改动 —— 那些留在每日流水里就够。

⛔ **写在"完成"那一刻**，不要攒。写日志的成本在事后会翻好几倍：判断依据在脑子里只保留很短的时间窗。

## 4 条目格式（一个条目一个文件）

落点：`logs/<YYYY>/<MM>/<id>.md`；`id` = `<date>-<kind>-<slug>`，**全局唯一**。

```markdown
---
id: 2026-09-25-decision-memory-backend
date: 2026-09-25
kind: decision            # decision | incident | milestone | change | note
area: memory              # 功能域（memory/sidebar/context/build/release/icons/guards/…）
title: 记忆后端二选一（内置金字塔 / MCP 记忆服务）
tags: [memory, mcp]
commits: [9308b62]        # 相关提交（让"这行代码为什么这样"能一路追到讨论）
files: [electron/memory-backend.ts]
importance: high          # high | normal
supersedes:                # 可选：被本条目取代的旧 id
---

# 标题

## 背景
（当时为什么会有这件事；用户的原始诉求/现象）

## 结论
（定下了什么。可执行、可验证，不要写成"优化了一下"）

## 依据
（代码路径 / 实测数据 / 用户原话。**能指向文件与行号最好** —— 这是半年后唯一能复查的东西）

## 影响面
（哪些模块、哪些行为、哪些其他结论会因此变化）

## 回滚
（怎么退回；不确定就写不确定，别装懂）
```

**写作要求**（照这条自查）：

- **背景里要有"当时我不知道什么"** —— 只写结论会导致下一个人重复推理
- **依据里禁止"已验证/测试通过"这种空话**：写清**怎么验的**（命令、判据、数据）
- **结论要能被否定**：写「X 时用 A，Y 时用 B」，而不是「视情况处理」
- 长度不设上限，但**别灌水**：这个目录的价值在于密度，不在于页数

## 5 索引机制（与 WorkBuddy 检索形态对齐）

`logs/index.jsonl` = **一行一条**的机器可读索引，字段：
`id / date / kind / area / title / tags / commits / files / importance / path / bytes / sha256 / archived`

对齐点（WorkBuddy 的检索是「单一入口 + 自包含查询 + 排序返回」）：

| WorkBuddy | 本目录的本地等价 |
|---|---|
| `conversation_search`（单一检索入口，跨会话） | `node scripts/logs.mjs search`（单一检索入口，跨全部日志条目） |
| 服务端相关度排名 | 纯本地打分：`命中数 × 字段权重（title 6 / tags 4 / id 3 / area-kind-files 2）× 30 天半衰期新鲜度` |
| 查询需自包含 | 关键词 + `--area/--kind/--tag/--since` 过滤，可组合 |
| 覆盖全部历史会话 | 覆盖全部条目（含归档段：`--archived true`） |

⛔ 差异（别指望它做这些）：**没有语义/向量检索**（纯关键词，中文按子串匹配）、**不跨会话原文**、**无云端排名**。
⛔ **索引是派生数据**：坏了就 `reindex` 从磁盘重建，**索引丢失不等于内容丢失**。

## 6 查看 / 检索 / 清理 / 删除

```bash
# 写（⛔ 正文一律 --body-file；用 --body "…" 时正文里的反引号会被 shell 当命令替换执行，
#   内容静默少一段而命令仍报成功 —— 09-25 实际踩到，两条条目正文被吃掉）
node scripts/logs.mjs new --kind decision --area memory --title "标题" --body-file .workbuddy/tmp/body.md

# 看
node scripts/logs.mjs list                      # 列全部（默认不含归档）
node scripts/logs.mjs list --kind decision --since 2026-09-01
node scripts/logs.mjs search 上下文 供应商        # 关键词检索（按相关度排序）
node scripts/logs.mjs search 图标 --area icons   # 带域过滤
node scripts/logs.mjs show 2026-09-25-decision   # 看内容（支持唯一前缀，不必敲完整 id）
node scripts/logs.mjs stats                      # 总量与分布

# 清理（= 移进 archive 段，内容仍在 git 里，随时搜回）
node scripts/logs.mjs archive <id...>
node scripts/logs.mjs archive --all-before 2026-06-01

# 删除（硬删，需二次确认 + 理由；**会留永久墓碑**）
node scripts/logs.mjs delete <id...> --confirm <id...|all> --reason "为什么删"

# 完整性（这三条是"不丢失"的可证明部分）
node scripts/logs.mjs reindex                    # 索引损坏/手工加过文件时重建
node scripts/logs.mjs verify                     # 缺文件 / 哈希不符 / 未入索引 ⇒ 非 0 退出
```

⛔ **删除的安全设计**（用户 09-25 要求"可删"与"不丢失"并存，这里是调和方式）：

- 删除**必须**给 `--confirm`（逐个列 id 或 `all`）**和** `--reason`（进墓碑，半年后靠它解释）
- 内容会被真删，但 `logs/audit-deletions.jsonl` 里**永久**留下：`id / path / bytes / sha256 / deletedAt / reason`
  ⇒ **"它存在过、是什么、指纹是什么"永远可查**，只是正文不在了
- 删除是**追加墓碑 + 重算索引**，索引里随之消失；`verify` 会把墓碑数一并报出来

## 7 什么在保护"不丢失"（按强度排序）

1. **`logs/` 进 git** —— 磁盘坏 / 换机器 / 误删工作区都能找回。⚠️ 因此本目录**必须提交**，不许被 gitignore 吃掉
   （已核对：`.gitignore` 里只有 `*.log`，所以条目**只能用 `.md`**，⛔ 别改成 `.log`）
2. **一个条目一个文件 + 追加写** —— 不覆盖历史；结论错了就新建条目 + `supersedes`，旧结论仍可查
3. **sha256 校验（`verify`）** —— 内容被改动/被截断能当场发现（实测：追加一行即报"哈希不符 + 大小不符"）
4. **索引可重建** —— 索引不是真相源，磁盘上的 `.md` 才是
5. **删除留墓碑** —— 正文可删，"存在过"不可删

## 8 给写日志的人（含 agent）的一段话

你会觉得"先写完代码再说"，然后就没有然后了。**日志不是交付之后的收尾工作，它是判断的一部分**：
写"依据"那一段时，你会发现自己其实没验过某个假设 —— 这一刻省下的返工，比写日志本身值钱得多。

判据很简单：**半年后的你，能不能只看这一个文件就明白"当时为什么这么定"**。不能，就是没写完。
