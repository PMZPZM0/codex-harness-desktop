# 压缩期间状态条挂「正在生成回复」+ 未压缩完就报成功：引擎把压缩跑成回合，宿主缺语义分支

## 现象

用户 09-26 连续两张截图：

1. 回合已结束（耗时显示出来了），时间线底部状态条仍挂「正在生成回复 · 正在落笔」，压缩分隔线还在转圈。
2. 压缩还明显在跑（分隔线转圈 + toast 提示），却已经弹出「上下文压缩成功」。

## 定性

两条都是**同一处语义错误**的两个面：引擎把「压缩上下文」跑成了一个**真实回合**（`turn/started` → 压缩 item inProgress → 完成），宿主侧对此没有对应的语义分支。

- **状态条挂住**：`runActivity` 兜底只看「有 inProgress item 但没命中 switch」→ 返回「正在生成回复」。压缩 item 不在 switch 里，于是压缩期间一律显示「正在生成回复」。更糟的是压缩的完成信号走 `thread/compacted` / `item/completed(contextCompaction)`，**不保证有 `turn/completed`** ⇒ `turn/started` 点亮的 `running/sending/activeTurnId` 没人熄灭 ⇒ 结束条件永不成立、状态条与停止键永久亮着。
- **成功提前**：`item/completed(contextCompaction)` 一到就 `setCompactEventState("success")`。引擎一次压缩可能产生**多个** compaction item，第一个完成就报成功；且 `thread/compacted`（权威完成信号）到达时，本地还挂着的 inProgress 压缩 item 无人落平 ⇒ 分隔线继续转圈，与「已成功」自相矛盾。

## 修法（三层）

1. **压缩不是生成回复**（`part06/02-seg/01-turn-runtime-activity.tsx`）
   - 扫描 item 时 `contextCompaction` 直接 `continue`（不落到任何「正在…」文案）；
   - 兜底前加闸：`compactPendingRef` 含当前会话 ⇒ 返回空串（状态条静默）。压缩的进度指示由分隔线转圈 + compact toast 承担，不占用状态条。

2. **压缩结束必须结算运行态**（新增 `bag.settleAfterCompaction`，落在 `part04/01-seg.tsx`）
   - 清 `sending` / `interrupting` / `activeTurnId` / `workStartedAt` + `markThreadStopped`；
   - ⛔ **反向守卫**：本会话还有**非 contextCompaction** 的 inProgress/running item 时**绝不动**——回合中途的自动压缩不许把真回合的运行态打停（「运行莫名停止」零容忍）；
   - 两个完成信号都接：`item/completed(contextCompaction)` 与 `thread/compacted`。

3. **成功提示只发一次 + 权威信号停转**（`part05/01-seg.tsx`）
   - `item/completed` 时先扫全量 turns：还有**别的** inProgress compaction item ⇒ 不发成功（等最后一个）；
   - `thread/compacted` 到达时把时间线里仍 `inProgress` 的压缩 item 落成 `completed`（不依赖引擎补发 completed，分隔线立刻停转）。

## 判据

守卫【163】（`scripts/guards/07-turn-fold.mjs`，7 条）：压缩 item 不计入活动文案 / 压缩中不兜底 / 两处完成信号都调 settle / settle 同时清 sending 与 activeTurnId / settle 有「真回合在跑不动」守卫 / 成功提示有 stillCompacting 闸 / thread/compacted 落平 inProgress。
变异验证：拆掉「压缩静默兜底」⇒ 红；去掉 settle 的 `setActiveTurnId(null)` ⇒ 红。

## 影响面与风险

- 只影响压缩期间的状态条文案与结算时机；正常回合（无 compaction item）路径完全不变（`settleAfterCompaction` 在 threadId 不匹配或无压缩 item 完成时不会被调用）。
- 已知边界：一次压缩产生多个 compaction item 且中间夹着真实工具调用时，成功提示会等最后一个压缩 item 完成才发——符合「成功了才说成功」。
- 未做真机复现（引擎把压缩跑成真回合的场景在探针环境里表现不稳定）；判据靠【163】静态守卫 + 变异，落地后由用户实际压缩验收。
