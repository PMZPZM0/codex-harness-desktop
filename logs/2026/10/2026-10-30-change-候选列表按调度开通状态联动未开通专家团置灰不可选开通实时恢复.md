# @ 候选列表按调度开通状态联动（未开通置灰不可选 / 开通实时恢复）

## 结论

用户要求「@ 唤出的选择列表按调度开通状态联动展示，未开通专家团时该项置灰不可选，开通后自动恢复为
可选中高亮，联动随开关实时更新，并与提示词描述保持一致」。

改动前：`agents:catalog` 下发的 targets **不按开关过滤**，@ 面板原样渲染 ⇒ 专家团一直可点，
真派活才被闸门拒。用户点得动却没有明确提示，只能靠失败后才知道没开。

## 改法（**置灰，不隐藏**）

| 层 | 改动 |
|---|---|
| 纯函数 `dispatch-mention.mjs` | 新增 `mentionKindAllowed(allow, kind)`（与主进程 `dispatchAllowOf` 同口径：专家/子智能体/CLI 恒可用，专家团跟随 `team === true`，缺键按关）；`filterMentionTargets(…, allow)` 给未开通的类别打**整组 `off` + 每行 `disabled`**（标记成新对象，不污染 `dispatchInfo.targets` 共享引用）；`flatMentionTargets` 跳过置灰行；`mentionEnterPlan` 区分「没有候选」与「候选全被置灰」 |
| 输入框 | allow 直接取顶层 `activeDispatch` ⇒ 拨开关即重渲染（真"实时"）；行用原生 `disabled` + `aria-disabled` + title，组挂 `is-off`；组标签改文案「未开通 · 在顶栏「调度」里打开后即可选」 |
| 样式 | `button:disabled` → `opacity .45` + `cursor: not-allowed`，hover 不上色；⛔ 不隐藏 |
| 提示词 | `electron/dispatch.ts` 补「输入框的 @ 选择列表 = 本段的许可范围」（置灰/实时恢复/该怎么回答用户）；`mentionBlockOf` 增第 ④ 条同口径话术 |

## 两处「读代码看不出来」的坑

1. **Enter 的双分支**：输入框先采纳 @ 候选，再采纳入历史消息。候选全被置灰时若只判断「没有可选候选」，
   会**继续落到第二条分支，把一条历史消息悄悄塞进输入框**。置灰的语义是「看见了但不能选」，
   正确反应是什么都不做 ⇒ `mentionEnterPlan().disabledOnly` 时 `preventDefault()` 直接返回。
2. **调度面板是「先改 draft 再确定」**：探针只点 `.dispatch-master-switch` 不落库（上一轮就是这样把
   "还原"做成了假动作，导致下一轮读到 `dispatch-on` 还在、误判"置灰没生效"）。探针必须先读
   `.dispatch-topbar-btn.dispatch-on` 把状态拨到预期，再断言。

## 判据（真机 CDP）

- 团关：`@专家团` → 该组 `is-off`，6 行全部 `disabled`、`opacity 0.45`、`cursor not-allowed`；
  点置灰行**不产生芯片**；按 Enter 后 chip / 正文 / 消息数**三者都不变**。
- 团开（顶栏「调度」打开并确定）：该组 `off=false`，行恢复 `disabled=false` / `opacity 1` / `cursor pointer`。
- `npm run build` 通过；`npm run check` 仅剩 1 条红（并行线【180】）；`check-app-dist` PASS；
  守卫 11f +9（纯函数真跑 + 渲染层接线 + 提示词同口径），100/100。
