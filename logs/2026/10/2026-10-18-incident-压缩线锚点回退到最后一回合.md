# 压缩线锚点回退到最后一回合

## 背景
用户 10-18 截图（会话「帮我看看我的workbuddy为...」）：发一条新消息后，「✅ 上下文已自动压缩」那条线
紧贴在新消息上方；用户原话：「这个压缩线什么情况啊，每次发新消息他都在上面，展示逻辑就不对啊，
没有跟着历史消息往上顶啊」。

## 结论
**不是锚点语义没写，而是"边界回合找不到"时的回退方向错了。**
- 大会话只加载**最近几页**回合（`resumeThreadWithTurns`：每页 200、最多 3 页、desc 取），
  而自动压缩常常发生在更早的历史里 ⇒ 压缩记录里的 `turnId` **不在已加载窗口**。
- 旧代码：`const anchorFrom = boundaryTurnId ? ordered.findIndex(...) : ordered.length - 1;`
  然后 `for (i = anchorFrom >= 0 ? anchorFrom : ordered.length - 1; ...)` —— 边界找不到就当作
  「最后一回合」⇒ 线被钉在最新消息上方、每来一条新消息跟着往下跑。
- 另有一个同型坑：旧代码用 `ordered`（全部已加载）里的回合去 `visible`（窗口内）取下标，
  窗口外恒 `-1` ⇒ 线凭空消失。

修法：把锚点抽成纯函数 `src/lib/compaction-anchor.mjs` 的 `resolveCompactionAnchor(visible, boundaryTurnId)`：
1. 边界在窗口里 ⇒ 从它往上找最近一条含 `userMessage` 的回合，插在那之上；
2. 边界**已知但不在窗口** ⇒ **窗口顶部**（它比手里的历史都早）；
3. 边界**未知**（只有 toast）⇒ 最后一回合（压缩就发生在当下）。
时间线的三条分支（引擎 item / 宿主记录 / 运行中）全部走它。

## 依据
- 真实数据核过：`<userData>/compaction-records/01a14891-….json` 里 5 条记录的 turnId 都在 rollout 里，
  但都**早于**最近 8 个回合 ⇒ 完全符合"边界在更早的历史里"。
- 守卫 `12r-compaction-anchor`（新，独立 + check 链）：6 条真值表（正向/反向/无 userMessage 窗口/
  空列表）+ 4 条接线与负向；**4 处变异全抓**（含"边界找不到 ⇒ 回退最后一回合"这条原 bug 原样复现）。
- 验收 `compact-line` 加 **⑥b**：压完再发一条消息，线紧接着的仍是**同一条**用户消息 —— 真机 **7/7**。
  ⛔ 同轮踩到并修的验收自身问题：10-17 的四态模型会先渲染一条**运行中**分隔线，
  旧选择器 `.compact-divider` 会抢先命中 ⇒ ④ 必假红；改成只等 `--settled` / `--success`（排除 `--running`）。
- `npm run check` 预检 exit 0。

## 影响面
- 只动渲染层锚点计算与验收；不改压缩侦测链、不改存档格式。
- 大会话里旧压缩线的位置会**上移**到已加载历史的顶部（语义正确：它确实比这些历史都早）。

## 回滚
- 回退 `70e7761`。只想临时改口径：把 `resolveCompactionAnchor` 里 `if (at < 0) return 0;` 改回
  `return list.length - 1;`（会复现「钉在最新消息上方」）。

## 口径（用户 10-18 定）
- 压缩线 = **历史项**：线停在它发生的那个回合上方；时间线默认只渲染最近 5 个回合（`TURN_WINDOW`），
  所以要往上翻 / 点「显示更早的消息」才看得到 —— **这就是期望行为**，不是缺陷。
- ⛔ 不许为了「平时也能看见」去自动扩渲染窗口、或把它钉在常驻位置（用户明确选了「历史项，翻上去才看」）。
- ⛔ 它也不属于「大折叠」：实测 `inFold:false`，运行中与已完成两条线都渲染在**回合之间**，
  不会被 `TurnFoldStream` 的过程折叠吞掉（那条路对 `isCompactionItem` 有显式剔除）。
