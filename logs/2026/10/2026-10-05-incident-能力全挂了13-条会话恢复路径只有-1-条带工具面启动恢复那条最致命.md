# 「能力全挂了」：13 条会话恢复路径只有 1 条带工具面（`176dd7a`）

## 背景
用户 10-05 报「全挂了」，检查表里 `scheduler_list` / `knowledge_search` / `ui_component_search` /
`video_status` / `voice_generate` / `workflow_read` 全部 `unsupported call`，只有 `agent_invoke` 正常。

## 结论
不是能力坏了，是**那个会话的工具面是它创建时的快照**，而恢复会话的 13 条路径里**只有 1 条**
把当前工具面带上了 —— 其中最致命的那条正是**应用启动时的自动恢复**。

## 依据（每一步都有硬证据）
- 引擎日志库 `D:\11\codex-home\logs_2.sqlite`（表 `logs`）：失败回合在 thread `01a109a2`
  （10:09:18 提交），该会话 **09:17:04 创建**，而能力网关 **09:56 才构建** ⇒ 工具面里没有网关工具。
- 引擎在 **10:05:11** 收到过该会话的 `thread/resume`；`D:\11\dispatch-port.txt` mtime = 10:05:08
  ⇒ **用户跑的就是新构建**。⛔ 这一步不做，用户会一直被要求"重启试试"，而重启解决不了。
- 渲染层 `thread/resume` 共 **13 条**（7 处直发 + 6 处走 `resumeThreadWithTurns`），带 dynamicTools
  的只有 `open-thread` 那一处；启动恢复走 `part06/01-seg/01-ui-ready-mood-refs.tsx`（不带）。

## 修法（结构性，不依赖"引擎认不认 resume"这个未验证前提）
`app-view/helpers/thread-list.ts` 的 `resumeThreadWithTurns` 是全应用唯一恢复入口（分页兜底也在此），
现在它**无条件附加当前工具面**；5 条直发路径改走入口、6 处既有调用补 `bag` 首参。
守卫 `11i` 17→20：直发点只允许 2 处 / 入口必须"取到并拼进"工具面 / 所有调用都传 `bag`。

## 影响面 / 未决
- ⛔ **引擎到底认不认 resume 上的 dynamicTools，本轮未验证**：09-16 的 `dispatch-core.ts` 说不认，
  `open-thread.tsx` 说 schema 接受，两条注释冲突。我用隔离 `CODEX_HOME` + mock provider + 真实
  app-server 做了 A/B/C 探针（start 不带 / resume 带 / start 带 = 阳性对照），
  **阳性对照也没注入** ⇒ 探针环境是 shell 模式（`exec_command`）而 App 是代码模式（`functions.exec`），
  工具面落点不同 ⇒ **结论不可用，已弃用**。不把"resume 生效"说成已解决。
- 用户侧确定可行：**新建一个任务**（dynamicTools 只在 `thread/start` 确定，引擎硬约束）。

## 顺带修掉的隐性脆弱点
`resumeThreadWithTurns` 的声明**漏了 `export`**，而 barrel 一直在 `export { … } from "./helpers/thread-list"`
转发它。之前能构建纯属侥幸 —— **函数签名一变** rolldown 立刻 7 个 `MISSING_EXPORT`（本次实测踩到）。

## 三条入库的教训
1. **探针必须有阳性对照，且要与被测环境同配置**；否则"什么都没看到"会被误读成"机制无效"，
   进而把一个未验证的结论写成"引擎不支持"。
2. **断言强度必须 ≥ 文案承诺**：`11i` 第一版查"函数体里出现 `dynamicTools`"，变异把赋值换成空数组
   仍然为真 ⇒ 假绿；改成分别钉"来源 = `await bag.buildDynamicTools()`"与"…`dynamicTools.length ? {dynamicTools} : {}`"
   两段接线后，M1/M2 两组变异才都如期变红。
3. **工具链两个坑**：多行文本锚点在 **CRLF** 文件上会全部锚空（补丁脚本要按文件实际换行符转换）；
   `build:vite`（rolldown）**不做类型检查**，`build:vite` 绿不代表类型对，必须另外跑 `tsc -b`。
