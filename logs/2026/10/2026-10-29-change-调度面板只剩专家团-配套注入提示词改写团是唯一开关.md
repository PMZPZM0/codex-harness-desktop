# 调度面板只剩专家团 + 配套注入提示词改写（团是唯一开关）

# 调度面板只剩「专家团」+ 配套注入提示词改写

## 用户令（10-29 追加两轮）

> 「这里就可以只剩一个专家团就行，展示优化一下」
> 「配套的注入提示词，要优化一下，摸清楚，连带的功能，再改」

## 为什么必须同时改面板与提示词（摸清后的结论）

面板与注入面是**同一件事的两个出口**，只改一个就会出现"界面已经没这个开关、模型还让用户去点"的错觉：

| 出口 | 位置 | 旧文案的问题 |
|---|---|---|
| 面板 | `DispatchMenu.tsx` | 三类并排开关里两个永远开着 ⇒ 纯噪音，还暗示"默认是关的" |
| 工具描述（模型每轮都读） | `dispatchToolDescription` + MCP 孪生 + 渲染层兜底 | 写着"本会话可调度：专家、子智能体"，且"未开启（不要派）"逐类否定 ⇒ 模型据此让用户去"勾选子智能体" |
| 会话内告知（注入下一条用户消息） | `dispatchSelectionChangeNotice` | 按"勾了几类"分段，暗示专家/子智能体也能被关 |
| 常驻指令第 6 条 | `developer-instructions.ts` REVIEW_INSTRUCTIONS | "this session has 调度 on, you may use it" ⇒ 把子智能体当成要开关的能力 |
| 被拒文案 | `dispatchKindAllowed` | 只说"没开"，不给"别再试 + 可改用谁" |

## 改法

1. **面板**：只剩一行「专家团」switch（带数量徽标、开/关各自的含义），下面一行只读说明
   「专家 N · 子智能体 M · 默认可用，无需开启」；确认时 expert/subagent 恒写 true。
2. **数据**：`normalizeDispatchConfig` / `dispatchAllowOf` 把 expert / subagent **恒读为 true**
   —— 界面已无关闭入口，旧记录里的 false 只会留下用户无法纠正的"禁用专家"状态。
3. **工具描述**：首句直接给结论（"专家/子智能体可直接派、不需要任何开关；专家团未开启，要团请用户打开，别硬试"），
   并加一条硬规则「**不要把「先去调度面板开启」当成前置条件**」；专家团的否定段只留一句。
4. **告知**：只有两态 —— 打开了团（带职责 + 名单）/ 关掉了团（明确 team/member 会被拒、别再试），
   两态都写明"专家与子智能体不受影响、不需要开关"。
5. **被拒文案**：给出"别再重复调用 → 请用户开团 / 改用专家或子智能体 / 自己做"。
6. **常驻指令**：子智能体改成"随时可用"，只有专家团需要用户开。
