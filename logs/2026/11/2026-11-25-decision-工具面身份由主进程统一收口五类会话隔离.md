# 工具面身份由主进程统一收口（五类会话隔离）

## 背景
用户三次反馈同一类症状：普通会话里「没有派活工具」，而另一些会话里工具又不对。根因不是权限判错，
是**所有权放错层**：身份类工具（`agent_invoke` / `agent_archive_sessions` / `agent_list_children`
三件套、`group_*` 九件套）由**渲染层**按 `bag.threadRole` 增删，而它只描述「当前显示的那条会话」。
切会话 / 新建会话时那一刻 state 还停在**上一条**上 ⇒ 新会话被贴上旧身份。加 await 只能改善某条路径，
下一种时序又会打穿。

## 结论
1. **唯一实现**：`electron/tool-surface.ts` 的 `IDENTITY_TOOLS`（工具名 → 能力位）+ `applyToolIdentity(tools, kind)`
   （纯函数）+ `splitIdentity(tools)`（划分）。⛔ 不复制能力矩阵 —— 矩阵仍只有 `src/lib/session-kind.mjs`
   的 `SESSION_CAPS` 一份，本模块只维护「名字 → 能力位」对照表。
2. **唯一写点**：主进程五处写面全部过表 —— `codex-ipc` thread/start（normal 常量）、thread/resume
   （目标会话 `hostKind`，来自主进程台账）、`delegation`（expert）、`teams-ipc` 主理人 + 成员（expertTeam）、
   `group-talk`（workPartner）。
3. **渲染层退出**：`part08/01-seg.tsx` 去掉 `caps.dispatch ?` 与 `caps.bossGroup ?` 两个门控，只提供
   与身份无关的能力面。守卫 11f 改为**负向**断言（谁把 caps 判定写回渲染层就红）。
4. **顺序定案**：先 `splitIdentity` → 其余走 CORE 画像收窄 → 身份类按类型裁后拼回。
   ⛔ 反序会把身份工具一起裁掉 ⇒ 同一条会话「新建时没有群工具、resume 一次又回来」（用户说的"乱套"）。
5. 顺带：`expert_save` 补 `displayNameZh` 校验（不再默认建出「未命名团队」垃圾条目）；
   `agents:dispatch-call` 拒绝 `RENDERER_DEDICATED`（堵掉"工具面没有却能从网关绕过"的隐性双通道）。

## 依据
- 端到端（重启后读 rollout 首行）：普通会话 27 个工具，派活三件套 + 群编排九件套齐全、`step` 在位；
  团队会话 `0c01df9d` 8 个、**无** `agent_invoke`、有 `team_member_invoke` —— 主会话与派生会话互不串。
- 纯函数真跑（11i 子进程 import TS）：normal/hub = 12 个身份工具；expert/expertTeam/workPartner/delegate = 0；
  幂等、不改入参、顺序无关、未知类型回落 normal；`splitIdentity` 是划分（不漏不重）。
- 名单对账：表里 9 个 `group_*` 与 `05-boss-group-tools.tsx` 的 `BOSS_GROUP_TOOLS` 逐条一致（守卫钉住）。
- 判据：tsc ×2、`npm run build`、`npm run check` **✗ = 0**；【265】棘轮无变长；11i 39/39、11f 203/203。

## 影响面
- 五类会话的工具面从此只由**自己的类型**决定，与"从哪切过来、怎么新建、跳几次"无关。
- **可见变化**：普通会话重新拿到群编排九件套（11-19 的 CORE 收窄曾把它们裁进网关，而网关没有这些分支
  ⇒ 实际上不可达）。这是按能力矩阵恢复，代价是每轮多约 9 份 schema。
- 专家 / 专家团 / 工作伙伴 / 被调度会话：身份工具恒为 0（此前靠渲染层状态，可能漏给）。
