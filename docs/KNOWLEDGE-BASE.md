# 知识库索引规范

> 适用范围：`<workspace>/.codex-harness/knowledge/`（随项目走，不进 git）。
> 代码真相源：`electron/knowledge-base.ts`（存储/分块/检索）、
> `electron/features/kb-embed-backend.ts`（向量后端）、`electron/features/knowledge-base-ipc.ts`（IPC 通道）。
> ⛔ **本文与代码不一致时以代码为准，并回来改本文**（本项目铁律：注释/文档声称的能力最危险）。

---

## 0. 一句话目标

**存进去的知识能被精准召回；召回结果不浪费 token。**

这两件事互相拉扯：召回少了漏答案，召回多了塞上下文浪费钱。本规范的所有条款都服务于这一句。

---

## 1. 存储布局

```
<workspace>/.codex-harness/knowledge/
  docs/<docId>.md      文档正文（原文，不加工）
  docs/<docId>.json    元信息 { id, title, source, chunks, addedAt }
  .cache/embeddings/   向量缓存（可随时重建，不进 git）
```

| 约束 | 值 | 出处 |
|---|---|---|
| 目录 | `<workspace>/.codex-harness/knowledge/` | `KB_DIR` |
| 文档数上限 | 500（超出需先治理，不静默丢弃） | `MAX_DOCS` |
| 单文件上限 | 20 MB | `MAX_FILE_BYTES` |
| 块大小 | ~700 字符 | `CHUNK_SIZE` |

⛔ `docId` 由标题派生（`safeId`）⇒ **同名标题会互相覆盖**。批量导入前必须去重（见 §5）。

---

## 2. 命名与元信息

- **标题即标识**：标题会派生 `docId`，重名 = 覆盖。标题里带上范围与日期，如
  `记忆金字塔规范 2026-10-04`。
- **来源要能追溯**：`source` 记录出处（文件路径 / URL / 手写），否则半年后没人敢删。
- **`addedAt` 是排序依据**，别手工改。

---

## 3. 分块规则

**现状**（代码事实）：按空行分段，段过长再按句号切，**块间带 80 字符重叠**（2026-10-04 实现）。

**为什么"块间不重叠"会漏召回**：一句话被切成"前半在块 3、后半在块 4"时，两块都不完整，
任何一边被检索到都答不全。分块的目的是"让每块自洽可答"，不是"让块大小均匀"。

**规范**：

1. **按语义边界切，不按长度切**：一个完整的定义/步骤/问答**不跨块**。
2. **宁可块大小不均，也不要把一个语义单元切开**。700 是软上限。
3. **表格与代码块整体保留**（它们被切开就不可读了）。
4. **块间重叠**：每块尾部重复上一块末尾约 80 字符，跨块句子因此至少在一块里是完整的。
5. **每块自带上下文头**：块首补一行 `文档标题 › 所属小节`（见 §4），
   否则一块被单独召回时读者不知道它在讲什么。

⛔ 上面的**第 4 条（重叠）2026-10-04 已实现**；**第 5 条（块首上下文头）还没实现**（见 §8 待办）。
写在这里是为了**规范先行**，实现前不要把文档改成"已支持"。

---

## 4. 每块应有的上下文（省 token 的核心）

一次召回返回的是**块**，不是整篇文档。块必须自解释，否则调用方要么多取几块（费 token）、
要么拿着无上下文的片段瞎猜（不准）。

每块检索结果应能回答三个问题，缺一个就补：

| 问题 | 缺失后果 | 补法 |
|---|---|---|
| 这是哪篇文档的哪一节？ | 不知道能不能信 | 块首加 `标题 › 小节` 上下文头 |
| 为什么命中？ | 无法判断相关性 | snippet 围绕 query 命中词取，不是取块首 |
| 命中了多少？ | 排序不可解释 | 返回 `score` 并在 UI 上显示排名依据 |

---

## 5. 接入流程（去重先行）

```
① 先查重：按标题 + 内容前 200 字符查 kb:list 与既有 md
② 命中 ⇒ 不新增；确需替换 ⇒ 手动删旧再增（工具不做自动覆盖）
③ 批量导入前先跑 §7 的体检
④ 导入后立刻用 2~3 个**真实问题**试召回，验不了就不算完成
```

⛔ **不要自动覆盖同名文档**。静默覆盖 = 知识丢失且无人察觉，这是最坏的一类 bug。

---

## 6. 召回质量标准（验收判据）

改任何检索相关代码，必须过这四条：

1. **精准度**：snippet 必须**围绕 query 命中词**取，不得固定取块首。
   ✅ 2026-10-04 已修（语义档原先 `chunk.slice(0, 260)` 取块首）；2026-10-10 进一步把**两档**的
   定位统一到 `snippetAround`（`electron/text-match.ts` 的 `bestHitIndex`，取最长命中 token 的位置）。
2. **两档量纲一致**：全文档与语义档的 score 放在同一张表里排序，不一致就要显式归一化。
   ✅ 2026-10-10 已修：全文档档归一到 0..1（`raw / maxChunkScore`），语义档直接用 cosine（去掉 `*10`）。
3. **低分不凑数**：低于阈值直接丢弃是对的（现状 `score < 0.25`），
   但阈值要与量纲匹配 —— 量纲变了阈值也要跟着复核。
4. **跨块不漏**：任取一句完整的话，用它当 query 应当能召回到包含它的块（验 §3 第 4 条）。
5. **中文无空格查询必须能召回**（2026-10-10 新增）：用户最自然的提问方式就是不带空格的中文短语
   （「记忆库容量」）。⛔ 原先全文档档用 `split(/\s+/)` 分词 ⇒ 整串当一个 token，只能命中**完全连续**
   的同一串 ⇒ 实测**召回 0 条**（加个空格才有）。现在统一走 `tokenizeQuery`（整词 + 中文双字 bigram）。
   守卫 `11-knowledge-base.mjs` 有端到端断言钉住（含"库里没有的词不召回"的反向断言）。

⛔ **"我跑了都没事"不算验收**。判据要落在召回结果本身：同一 query 两次跑，
`title + chunkIndex + score` 必须稳定可复现。

---

## 7. token 预算原则

- **召回上限 `limit` 默认 12、上限 20**（`searchDocs`）—— 不要为了"保险"调大。
- **snippet 上限 260 字符** —— 够看清一段话，不够就是一整块该被切小。
- **块大小 ↑ ⇒ 每块 snippet 覆盖的内容 ↓**：块越大越省"条数"，但越费"每条字符数"。
  两者要一起看，不能只调一个。
- ⛔ **不要把整篇文档塞进上下文**。知识库的价值就是"只取相关的块"。

## 9. Laya 软增强（2026-10-04 立项，2026-10-05 按校准定案）

Laya（本地 System 1 决策引擎，`laya-service.ts`，~33ms/次）在知识库上做**可选**增强，
服务未装/未就绪/超时/低置信一律弃权放行（fail-open，守卫判据 8 钉住）。

**⛔ 阈值与问法不是拍的 —— 跑 `node scripts/calibrate-laya-kb.mjs` 实测**（需 laya 已装，
权重走 ~/.cache/huggingface）。10-05 校准结论（fixture：12 门禁 + 5 重复 + 6 过滤）：

| 接缝 | 位置 | 校准结论 | 生产配置 |
|---|---|---|---|
| 写入门禁 | 模型工具 `knowledge_add`（UI 手动路径不接） | ✅ 可用：真知识 6/6 判对（0.79+），0.5 档拦 4/6 废话、**误杀 0** | knowledge/chatter 两分类问法，`minConfidence: 0.5`，判 chatter 才拒写 |
| 重复拦截 | `knowledge_add` 写入前，全文捞最像 3 条判 duplicate/new | ✅ 可用：4/5 判对，错在漏放方向（宁可放过） | `minConfidence: 0.5`，判 duplicate 拒写并给出已有条目 |
| 检索过滤 | ~~`knowledge_search` 结果逐条判相关~~ | ❌ **不可用，已砍**：三种问法模型都把一切候选判 relevant（0.80+ 置信） | 无 —— 想加回来必须先重跑校准并推翻此结论（守卫负向断言钉住） |

**校准另抓出的两个坑（已修/已记）**：
1. ⛔ 判定置信必须读 **`answer_confidence`**（所选答案的校准概率，0.5~0.99 档）；
   `confidence` 是**行动门限**（实测可能低到 0.10），拿它当判定置信会把全部判断弃权掉
   （`parseVerdict` 统一口径，守卫钉住）。
2. laya-serve 的 answers 按**问题名**键控，不是按选项名 —— 校准脚本第一版在这翻过车。

⛔ 纪律：**不为一次判断拉起 laya 服务**（~700MB 权重）——沿用思考档「就绪才用 + 后台预热」口径；
UI 的 `kb:search` 不掺模型判断（用户手动检索要确定性排序）。
