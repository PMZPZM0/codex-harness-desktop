> 起因：用户问「应用级的前端后端设计缺陷有没有」。此前三轮审计都在渲染层内部（滚动/性能/交互），

> 每条都给证据行号（会随改动漂移，附可 grep 的片段）与最小修法。

## P0 · 安全（建议立刻处理，改动前需确认产品行为）

### S1. 手机远控面**完全没有鉴权**，且监听全网卡 + 自动放行防火墙 + 可开公网隧道
- 证据：`electron/main.ts` 每次启动无条件 `try { await remote.start(); }`；
  `electron/remote.ts:89` `this.server.listen(this.port, "::")`（**全网卡双栈**）；
  `remote.ts:148-159` 自动 `netsh advfirewall firewall add rule ... dir=in act=allow`；
  `remote.ts:104-125` 还会起 `cloudflared` 公网隧道；
  路由侧 `/api/rpc`（send-message / new-thread 直接透传引擎，`remote.ts:463-479`）、
  WS 握手（只从 URL 取 `code`，**从不比对**，`remote.ts:520-551`）、根路径直接 302 到手机对话页。
- **已独立复核**：全文件搜 `pairCode|code ===|code !==|authorization|Bearer|token` 只命中一处
  `if (code === 0) return;`（netsh 退出码）——**没有任何凭据校验代码存在**。
- 配套放大器：`main.ts:326-333` 的 `remote.newThread` 写死 `sandbox:"danger-full-access"`
  + `approvalPolicy:"never"`。
- 后果：同网段任何人（或任何拿到隧道域名的人）**不需要配对码**就能开一个全权会话，
  在用户机器上执行任意命令、读写任意文件。这是整个项目最高危的一条。
- 最小修法（保持手机远控可用）：① WS 握手与 `/api/rpc` 校验一次性配对 token（`remote.pairUrl()`
  里那个 code 必须由手机回传并比对，失败直接 401）；② 默认只绑 `127.0.0.1`，
  需要局域网时显式打开（同时**不要自动加防火墙规则**，改成一次性提示）；③ 隧道默认关闭。

### S2. 自更新链无签名/无哈希校验，下载地址与安装路径由渲染层任填
- 证据：`electron/updates.ts:174-221` `downloadUpdate` 只落盘不校验；`LatestInfo.sha256`
  （`updates.ts:39`）从下发到使用**全链路没人比对**；`updates.ts:232-237` `installUpdate`
  就是 `shell.openPath(filePath)` 直接执行安装包；`updates.ts:180` 明确允许 `http` 明文；
  IPC 侧 `main.ts:3714 updates:download` 接受渲染层任给的 `downloadUrl`，
  `main.ts:3739 updates:install` 接受任给路径。
- 后果：坏发布站 / MITM / 渲染层被注入 = 用户视角「正常安装更新」的静默 RCE。
- 最小修法：① 下载后**必须**比对 `sha256`（缺失即拒绝）；② 只允许 https 且域名白名单；
  ③ `updates:install` 不接受渲染层路径（安装包由主进程自己记在内存里）。

## P0 · 不可恢复 / 数据丢失

### S3. `custom-model.json` 非原子写 + 启动链裸 await ⇒ 文件写坏后**永远打不开窗口**
- 证据：`main.ts:890-897` `readCustomModel` 对 `JSON.parse` 失败直接 throw（只有 ENOENT 返回 null）；
  `main.ts:1856` 是 `const custom = await readCustomModel();` 裸 await，位置在 `createWindow()`
  （1903）**之前**；整条 `app.whenReady().then(async () => {...})`（1832→2048）**没有 `.catch()`**
  ⇒ unhandled rejection 掐断启动链，窗口根本不创建。
  同文件有 10 处 `fs.writeFile(customModelFile, ...)`（5794/5812/5843/5872/5900/5915/5938/6019/5971/6023）
  是截断式写入，且 read-modify-write **无串行化**（set-model / set-effort / set-enabled / upsert /
  remove + 渲染层"打开会话对账 effect"多个写者）。
  preflight【5】只白名单校验三处已知 await，看不见这两处。
- 最小修法：① 写盘改「临时文件 + rename」原子替换；② 读失败降级为 null + 把坏文件改名备份
  （`custom-model.json.bad-<ts>`）+ toast 告知，绝不 throw；③ `whenReady().then(...)` 补 `.catch()`
  （至少落盘日志 + 兜底 `createWindow()`）；④ 同一文件的读改写收敛到主进程的单条串行队列。

### S4. 退出/更新时引擎会被「自动重启」（孤儿进程 + 抢占用）
- 证据：`electron/codex-server.ts:165` 把 `exit` 事件直接接到 `fail()`；`fail()`（288-305）
  无条件 `void this.restart()`；而 `stop()`（226-230）只 `kill()` **不摘监听** ⇒
  `cleanupAll()`（`main.ts:6099-6117`，退出路径）里的 `server.stop()` 会在退出过程中
  把引擎**重新 spawn**（孤儿 `codex.exe`，占同一份 `codex-home`）。
  更糟：`main.ts:2834` 的引擎自更新先 `server.stop()` 再替换 `codex.exe`，
  自动重启会和文件替换抢占用。
- 最小修法：`stop()` 里先 `this.proc?.removeAllListeners("exit")`（或置 `this.stopping = true`
  让 `fail()` 不重启），再 kill。

## P1 · 契约与边界（结构性，建议单独立一轮）

### A1. 这个应用实际上**没有 API 层**
`electron/main.ts` 269 处 `ipcMain.handle`，`electron/preload.ts` 284 处 `invoke`（+12 个事件通道），
`src/vite-env.d.ts` 手工同步 —— **纯 1:1:1 手写**，无 registry、无入参 schema、无统一错误封装
（有的 throw、有的 `{ok:false,error}`、有的只 `onNotice`）。唯一守卫是 preflight 的括号深度扫描器，
它能保证"三处没漏"，保证不了"接口设计得对"。**加一个能力要改三处**，一年下来 270 个通道没人说得清契约。

### A2. 边界收缩在「通道名」，没收缩在「值」
`preload` 把高危能力原样透出且不校验参数：`fs:write {path, content, root}`（**root 由渲染层给**，
沙箱边界由被约束方自己声明）、`ssh:exec {server, command}`（任意命令）、
`shell:reveal` / `external:open` / `browser:popout` / `terminal:input`。
而渲染层**要渲染模型输出**（markdown / 链接 / 市场条目的标题与描述）—— 那里一旦有注入，
攻击面直接是「本机任意文件写 + 任意命令执行 + 装任意安装包」（与 S2 合流）。
最小修法：`root` 由主进程维护、`external:open` 限制协议白名单、ssh/terminal 不接受渲染层构造的 server 对象。

### A3. `codex:request` 是裸透传，全仓库没有一条 allowlist
`preload.ts` `request: (method, params) => ipcRenderer.invoke("codex:request", method, params)` ——
渲染层可调任意引擎 RPC（含 `thread/delete`、`turn/interrupt`、`config/*`）。引擎协议动态，
透传有其道理，但配合 A1 意味着**这个应用没有任何一处"允许做什么"的声明**，只有"能做什么"。

### A4. 「零阻塞宿主」铁律被局部化，同类问题在别处仍在
硬约束只管 `codex:request` 链（preflight【6】守卫），但同一进程里其它 handler 照样同步读盘：
`main.ts:2326 appendFileSync`（日志）、`2674 readFileSync`（custom-model）、`3754`（插件清单）、
`3800`（package.json）。这些调用期间**所有会话**的事件转发一起停摆 —— 规则守住了"那一条链"，
没守住"那一类问题"。修法：把不变量收敛成统一封装（`safeRead/safeWrite` + 禁止裸 `fs.*Sync` 的守卫），
而不是一个函数名黑名单。

## P0/P1 · 主进程↔渲染层完整审计（10 条，按严重度）

> 与上面 S1-S4 同源，这里补全其余。第 1/2/3 条安全、第 4 条持久化、第 5/6 条生命周期、

### S5. 渲染层入参没有统一校验层，path/id 直接当文件系统与 shell 目标
`commands.ts:246-248` `deleteCustomCommand()` = `fs.rm(filePath)` 无包含性校验（渲染层任意字符串直达，
`main.ts:5244`）；`saveCustomCommand` 的 `prevFilePath` 同样裸 `fs.rm`；`main.ts:4124` `fs:write` 的
**工作区根 `root` 由渲染层自己传**（`path.relative(root, resolved)` 形同虚设）；`main.ts:802`
`voice:profiles-save` 用 `path.join(root, draftFile)` → `../` 可穿越；`main.ts:5626` `external:open`
放行 `file:`（→ `file:///C:/.../x.exe` 交给系统执行）。
**另两条同源缺口**：`main.ts:1866` `protocol.handle("harness-image", …)` 对 URL 里的 `path` 不收敛就
`net.fetch(pathToFileURL(path))`（全局协议）；全仓 grep `setWindowOpenHandler|will-navigate|will-attach-webview`
**零命中** → 主窗口与 `<webview>` 都没有导航/新窗口收敛（`BrowserPane.tsx:229` 的 webview 无 partition、无 allowpopups）。
全仓只有 3 处 `path.relative`，**没有 `resolveInside` 这类公共校验函数**，也没有统一 handler 包装。
修法：统一 `ipcMain.handle` 包装 + `resolveInside(trustedRoots, p)`；`harness-image` 限定 images/工作区；
`file:` 只允许工作区内 .html；主窗口 deny 导航并转 `openExternal`；webview 独立 partition。

### S6. 运行态副本没有收敛机制：`engineActiveTurnIds` 只会被 `turn/completed` 清理
`main.ts:277` 声明，只在 `1914-1915` 增删，**全仓无 `.clear()`**；而它的消费点是「等空闲」的阻塞循环：
`main.ts:2828-2832`（引擎更新前最多等 10 分钟）与 `3914-3918`（装运行时后同样等 10 分钟）。
引擎崩溃/自动重启后永远不会再收到 `turn/completed`（见 S4）→ 临时状态变永久状态：
以后每次「引擎更新」或装运行时都会显示「等待当前任务结束后开始替换…」并**白等 10 分钟**。
同一类收敛缺失：`main.ts:6119-6131` `window-all-closed` 无差别 `cleanupAll()`（杀引擎/停远控/停调度/停渠道），
但 macOS 不 `app.quit()`，`activate` 只 `createWindow()` → 关窗再点 Dock，**定时任务/渠道/远控永久不再启动**。
修法：`engineActiveTurnIds` 加 TTL 或由引擎快照重建；`window-all-closed` 与 `before-quit` 拆开，`activate` 补跑启动副作用。

### S7. IPC 没有统一请求/响应/错误形状，错误语义靠**中文文案子串**承载
`codex-server.ts:277` 丢掉引擎错误的 `code`/`data`，只留 `new Error(message)`；重启时所有在途请求被换成
同一句 `"Codex app-server restarted"`（`:132`），崩溃换成 `"Codex app-server exited (1)"`（`:165`）→
渲染层无法区分「可重试的中断」与「引擎真没了」。主进程只能**按字符串正则**决策：`main.ts:2525-2533`
命中 `/app-server restarted/i` 就退避重试，而重试**不区分幂等性**（`turn/start`、`thread/start` 也在内，
可能重发一句话/多一个空会话）。handler 层两套约定并存（throw vs `{ok:false,error}`）。
**最脆的一处**：`App.tsx:10040` `if (event.message && event.message.includes("重启"))` ——
引擎恢复状态机以文案为输入，**改一句提示文案就悄悄关掉「引擎重启后恢复视图」这条路径**。
修法：统一信封 `{ok:true,data}|{ok:false,error:{code,message,data}}` + 渲染层 `unwrap()`；
重试只对白名单幂等方法；状态事件加结构化 `reason`，禁止匹配文案。

### S8. 同一事实的真相源清单：以下 6 项**没有单一权威**
| 事实 | 真相源 | 权威性 |
|---|---|---|
| 会话列表 | 引擎 `thread/list` / rollout 文件（worker 缓存）/ 渲染层 `threads` / 主进程 `threadCwd`+`captureBuffers` | 靠 `session-tools.ts:17-53` 融合，谁都不是权威 |
| 运行中回合 | 引擎事件 / 主进程 `engineActiveTurnIds` / 渲染层 `runningThreadIdsRef`+`activeTurnIdRef` | 引擎权威，两个副本不收敛（S6） |
| 会话模型 | `localStorage["thread-model-<id>"]` / `custom-model.json` / `config.toml` / 每轮 `turn/start.model` | 引擎权威，四处靠手写对账 effect |
| 订阅态/余额 | **渲染层** `localStorage["relay-active-v1"]`（`lib/relay.ts:22-29`）/ `custom-model.json` enabled / config.toml | **无权威**，靠 `main.ts:5832` 广播事后对齐 |
| 沙箱与审批策略 | **只有渲染层** localStorage（`App.tsx:7492-7508`），主进程无记录、原样透传 | **无权威**，渲染层任填即生效 |
| 工作区→记忆归属 | 渲染层 `localStorage.workspace` / 主进程 `threadCwd` / 引擎 `thread.cwd` | 主进程副本会缺项 → 记忆落到全局层 |

具体后果：① 旧版/换机/清缓存后 `App.tsx:7493-7498` 的版本化迁移会把沙箱**静默写回
`danger-full-access` + `never`**（用户上次选的 read-only 消失，无提示，任何渠道/远控会话都跑全权）；
② rebase 后 `relay-active-v1` 与真实供应商不一致时余额徽标/订阅卡残留或提前退场；
③ 记忆分层会静默写错层（全局 vs 项目），事后无法追溯。
修法：每项事实指定唯一权威（运行时态 → 引擎快照；用户偏好与**安全策略 → 主进程文件且由主进程校验**
`thread/start` 的 sandbox/approvalPolicy，渲染层只是视图）；`relay-active-v1` 移到主进程。

### S9. 15 条事件通道各自为政（无信封/无序号/无背压），且「按会话裁剪」其实是空转
`preload.ts` 并列 15 个订阅 API，payload 形状各异、**没有一个带单调序号**；`main.ts:1904-1905` 每个引擎
通知直接 `webContents.send`（无合帧、无丢弃策略、无水位）。`main.ts:114-126` `filterForRenderer()` 对非当前
会话事件**只 `rendererDroppedEventCount += 1` 然后照样 return event**（注释自陈「临时回退为放行」），
而该计数以 `droppedForInactiveSession` 暴露给性能计数 —— **指标与事实相反**，会把后续排查带偏。
`main.ts:192-200` 渲染进程崩了就 `contents.reload()`，重载窗口内事件直接丢、渲染层无 gap 检测。
修法：统一信封 `{channel, seq, payload}` + 渲染层 seq 跳变即重拉快照；delta 类按帧合帧；
`filterForRenderer` 要么真裁剪要么改名去掉 drop 语义；终端/语音通道加水位与丢弃计数。

### S10. 主进程里塞进了渲染层知识；架构守则是「两个函数名」的黑名单
依赖方向反转：`main.ts:82-126` 主进程保存「屏幕上是哪个会话」（`rendererActiveThreadId` +
`RENDERER_CROSS_SESSION_METHODS` 白名单）；`main.ts:2515-2598` 通用转发器里按 method 名做业务分支
（`thread/list` 拼 rollout 兜底、`thread/resume` 打点、`Model provider ... not found` 时**就地改 config.toml
并重启引擎**再重试 —— 会话层修复逻辑长在传输层里）；`main.ts:1955/1962/4227/4253/5832` 用 `harness:event`
直接下发拼好的中文 UI 文案；`main.ts:2784` `app:perf-counters` 是按 e2e 断言形状设计的接口。
守卫的洞：`check-preflight.mjs` 的零阻塞守卫是 `SYNC_IO_CALLS = ["listRolloutThreads","enrichRolloutTools"]`
—— **两个函数名的黑名单**，于是同类同步 I/O 合法存在：`main.ts:5135` 同步 `applySessionsBackup`
（`thread-backup.ts` 全 `readFileSync/writeFileSync`，导出大历史会冻结所有会话的事件转发）；
`codex-server.ts:194-202` 每个 stderr chunk 都 `statSync + appendFileSync`，且 >2MB 时 `rmSync`
**整份删除**（历史证据一次性丢光）。
诊断侧：`/doctor`（`main.ts:2651-2727`）只给环境清单，**没有引擎 stderr 尾部、没有最近失败请求**，
引擎没起来时还显示误导性的「发起一次对话会自动拉起」；`codex-server.ts:70-72` 的**看门狗是空实现**
（2026-09-09 已移除）→ UI 里那个开关是死的。全链路无 requestId/traceId 贯穿，一次用户操作在三份日志里无法对齐。
修法：主进程只提供 `subscribe(threadId)` 式能力接口与结构化字段，文案/裁剪归渲染层；provider 别名修复抽成
独立服务；守卫从函数名黑名单改成结构性规则（main.ts / 非 worker 模块出现同步 fs 即失败，并给
thread-backup、codex-server 做同样的 worker 迁移）；删死开关或接回实现；加 traceId；`/doctor` 附最近 N 条
引擎 stderr 与失败请求。
