# 生图 / 修图 —— 工具拆分与交互流程设计（10-09）

> 用户提问：① 「PSmini」这个命名是否合适、能否清晰区分"生图"与"PS 编辑图"两类能力？
> ② 如何把两类能力拆成相互独立的工具、避免共用？③ 生图之后若只是小幅度改动，Codex 应主动询问
> 「用 PSmini 改图」还是「重新生图」——请提前规划完整交互流程与工具定义。

---

## 一、命名评估：「PSmini」不合适（建议不用）

| 问题 | 说明 |
|---|---|
| **商标风险** | "PS" 是 Adobe Photoshop 的通用代称，Adobe 对 "PS" 类命名维权积极。内置在商业应用里的**工具名与界面名**带 PS，是实打实的法律暴露面。 |
| **语义不自明** | 模型与用户都看不出"这是改图工具"。`image_edit` 一眼即"编辑图片"，且与 `image_generate` 天然成对。 |
| **与既定家族不一致** | 你先前拍板的调用面就是**「独立 image_* 工具集」**，插一个 `psmini` 是异类，模型要在两套命名风格间切换。 |
| **"mini" 误导** | 让人以为功能被阉割；实际它是 20 种确定性操作 + 合成 + 批次 + 格式转换。 |
| **中文语境** | 「PS 一下」在口语里泛指修图，但作为正式工具名不专业，也不可检索。 |

**推荐命名**

| 层面 | 建议 | 理由 |
|---|---|---|
| 工具名（模型可见） | `image_generate`（生图）/ `image_edit`（修图） | 成对、自明、无商标风险；**且已是现状实现** |
| 界面名（用户可见） | **「图像工坊」**（现状）或「修图台」 | 已有浮层就叫图像工坊，不必再造一个词 |
| 若一定要中文短代号 | **「修图」/「微调」** | 不要用 PS |

> 结论：**不用 PSmini**。真要区分，区分点应落在"生图 vs 修图"这两个动词上，而不是借一个第三方软件名。

---

## 二、两类能力的边界（可操作的判据）

两条路线的**成本模型完全不同**，这正是必须拆开的根本原因：

| | 生成族 `image_generate` | 编辑族 `image_edit` |
|---|---|---|
| 干什么 | 从文字**造出新内容** | 对已有像素做**确定性变换** |
| 依赖 | 生图插件凭证（API 地址 + 密钥 + 模型） | **零配置**（本地 jimp） |
| 成本 | 花钱、几秒~几十秒、结果不确定 | 免费、百毫秒、结果确定可复现 |
| 原图 | 无（凭空造） | **不覆盖原图**（产出 `<名字>-edit.<ext>`） |

**归属判据（给模型的硬规则）**

| 用户诉求 | 归类 | 走哪个工具 |
|---|---|---|
| 裁剪 / 缩放 / 旋转 / 翻转 | 几何 | `image_edit` |
| 调亮暗 / 对比度 / 饱和度 / 灰度 / 棕褐 / 反相 / 自动色阶 | 色调 | `image_edit` |
| 模糊 / 高斯 / 马赛克 / 色阶化 | 效果 | `image_edit` |
| 转格式 / 压质量 / 改体积 | 编码 | `image_edit` |
| 加水印 / 叠另一张图 / 加一行英文文字 / 压成纯色底 | 合成 | `image_edit` |
| **换主体**（狗换成猫）/ 换风格 / 换构图 / 换姿势 / 换背景内容 | 语义 | `image_generate`（重画） |
| **擦掉画面里的路人 / 局部重绘** | 语义 | ⚠️ **当前做不到** —— 见 §5 缺口 |

> 一句话：**改"形"用 `image_edit`，改"意"用 `image_generate`。**

## 三、工具拆分与定义（现状 + 定义）

四件套已经各自独立：**工具名独立、执行通道独立、凭证独立**（生图要 Key，其余三个零配置）。

| 工具 | 归属 | IPC 通道（各自独立） | 参数 | 要凭证 | 弹浮层 |
|---|---|---|---|---|---|
| `image_generate` | 生成族 | `image-lab:generate` | `prompt`(必) / `count` / `size` / `negative` / `model` / `workspace` / `name` | ✅ | 弹 → 完成自动收起 |
| `image_edit` | 编辑族 | `image-lab:edit` | `path` \| `paths` / `ops[]`(必) / `output` / `format` / `quality` | ❌ | 先亮源图 → 换产物 → 自动收起 |
| `image_info` | 编辑族 | `image-lab:info` | `path` \| `paths` | ❌ | 不弹（纯读） |
| `image_view` | 编辑族 | `image-lab:view` | `path`(必) / `title` | ❌ | 弹，**不自动收**（给人看） |

> ⛔ **图像族不在 `agents:dispatch-call` 能力网关里**（那条通道只服务其余 25 个能力）。
> 用户 10-09 原话：「工具区分开，不要共用一个工具」+「把生成和编辑的 IPC 也彻底分开，不要混在一起」。

**避免共用的三条硬约束（已落实）**

1. **凭证分离**：生图要 `builtin-plugins.json` 的 `image` 段；编辑族完全不读插件配置 —— 生图没配凭证时，修图/读信息/预览**照样可用**。
2. **实现分离**：生图走 `generateImageResilient`（HTTP 打网关）；编辑走 `image-lab.ts` 的 jimp 内核。两者不共享执行代码。
3. **名字分离**：四个工具名互不重叠，`ops` 里也没有任何"顺带生成"的操作。

⚠️ **唯一共享项是渲染层浮层**（`image-lab:event`）——那是**展示通道**，不是能力通道。四类工具共用一个弹窗组件是合理的（用户体验一致），不违反"不共用同一个工具"。

## 四、完整交互流程（生图 → 小改动 → 主动询问）

```text
用户：画一只戴墨镜的柴犬
   ↓
Codex → image_generate{ prompt }            [要凭证]
   ↓ 返回本地路径 P（浮层弹出→自动收起）
Codex 回复：图已生成 + ![柴犬](P)
   ↓
用户：把它的墨镜改成红色          ← 「同一张图 + 局部改动」= 两可区
   ↓
Codex 必须**先问**，不许直接动手：
   agent_ask{
     question: "这张图要改墨镜颜色，你希望怎么改？",
     options: [
       "修图：保留这张，只改局部（更快、不消耗生图额度）",   ← 推荐项在前
       "重新生成：按新描述重画一张（会消耗额度，构图可能变）"
     ]
   }
   ↓
┌─ 选「修图」→ image_edit{ path:P, ops:[…] } → 产出 P-edit.png（原图不动）
│                                           → 浮层亮产物 → 自动收起
└─ 选「重新生成」→ image_generate{ prompt:"…红色墨镜…" } → 新图
```

### 4.1 什么时候问、什么时候不问（防滥用）

**只有三条同时成立才问**：
1. 本会话里**刚产出过一张图**，且能拿到它的路径（`image_generate` / `image_edit` 的返回）；
2. 用户的新要求指向**同一张图**（"这张 / 它 / 刚才的 / 上面那张"）；
3. 改动落在**两可区**（颜色 / 明暗 / 大小 / 加字 / 加水印 —— 修图能做；但描述里又像在说新画面）。

**以下情况不问，直接干**：
- 用户说「裁一下 / 缩到 800 / 转成 jpg」→ 明确是修图 ⇒ 直接 `image_edit`；
- 用户说「重新生成 / 换一张 / 再来一版 / 换成猫」→ 明确是重画 ⇒ 直接 `image_generate`；
- 本会话没有可改的图 ⇒ 直接生图。

### 4.2 询问的呈现形式

复用现成的 `agent_ask` 工具（渲染层会弹成选项卡，第一项高亮为推荐）。**不新增工具**。

### 4.3 用户选了「修图」但编辑其实做不到

编辑族是**确定性操作**，遇到"擦掉路人 / 把狗变猫"这类语义诉求，它做不了。两条兜底：
- **事前**：Codex 按 §2 判据先自检，写不出对应 `ops` 就直接说明"这属于重画，不是修图"，跳过提问直接重生；
- **事后**：`image_edit` 遇到不认识的 `op` **明确报错**（不静默跳过），Codex 据此改口。

这条规则必须**常驻下发**给模型，否则不会被遵守 —— 落点见 §6。

## 五、缺口与要提前规划的扩展

| 缺口 | 影响 | 规划 |
|---|---|---|
| **无局部重绘（inpaint）** | "擦掉画面里的路人""只把墨镜换色"这类**语义级局部改动**做不到 —— 只有"整体重画"或"纯像素操作"两个极端 | 若要补：新工具 `image_inpaint{ path, mask?, prompt }`，走生图插件（图生图/编辑端点），**要凭证**。接口先留出来 |
| **无 AI 变体** | 想要"同一提示词 4 个变体"目前只能 `count`（同提示词硬出），不是基于某张图 | 可加 `image_variants{ path, prompt, count }`（图生图），要凭证 |
| **文字仅 ASCII** | 图上写中文是空白 | 需引入 CJK 位图字体；已记入限制 |
| **撤销** | 无需做 —— 编辑**从不覆盖原图**，产出新文件，天然可回退 | 保持并明确写进说明 |

**扩展原则**：语义类能力（inpaint / variants）属于**生成族**（要凭证、花钱、结果不确定），新增时挂在生成族一侧，**不要**往 `image_edit` 里塞 op。
