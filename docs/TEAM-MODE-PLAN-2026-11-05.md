# 团队模式（Team Mode）· 结合方案

> 输入：`飞书机器人群聊-逆向结论.md`（协议层）+ `豆包工作伙伴-团队模式-复刻方案.md`（治理层）
> 产出目标：在本应用内落地「多伙伴 + 群 + 记忆分级 + 成本归因」，不依赖飞书也能跑；将来要接飞书时协议不用改。

---

## 0 结论先行

三件事，一个关键取舍。

**三件事**
1. **群 = 聚合视图**，不是新会话类型。群订阅 N 个子会话的消息流，按时间合并展示。
2. **伙伴 = 现有专家团成员**，只加 3 个字段（`groupId` / `canDelegate` / `managerId`），不新造 agent 模型。
3. **先补两个事后补不回来的字段**：记忆的 `origin`（这条谁写的、从哪来）、账本的 `source`（成本归因维度）。

**关键取舍（决定整件事的复杂度）**

⛔ **不把多个 agent 塞进一个引擎 thread。**
引擎的 thread 是「单 agent 对话」模型（一个 session_meta、一条 rollout、一套工具面）。硬塞多 agent 发言，等于伪造 role/author，会让历史、记忆归属、压缩全部失真。

✅ 正确做法：**群是视图层**——每个伙伴一个自己的 thread（现有子会话机制），群负责把这些 thread 的消息按时间轴聚合 + 加 `author` 装饰。这和飞书"群成员各自是独立账号"的模型其实一致。

## 3 最小数据模型

```ts
// 群（视图实体，不持有消息本体）
type Group = {
  id: string;                    // grp_xxx
  name: string;
  memberIds: string[];           // = 专家团成员 id
  leadId: string;                // 主理人（可删机器人/可派活）
  guard: {
    scope: "project" | "dept" | "all";   // 部门/项目范围
    allowExternal: false;                // 默认禁外部
    respondToBotMentionOnly: boolean;    // 只响应被 @ 的机器人消息
  };
};

// 伙伴关系（组织树 = 委派白名单，不是进程树）
type PartnerLink = {
  agentId: string;               // 成员 id
  managerId?: string;            // 上级
  canDelegate: string[];         // 只允许派给这些
  groupId: string;
};

// 消息投影（群视图里的一条；真身仍是子会话的 item）
type GroupMessage = {
  id: string;                    // msg_xxx
  groupId: string;
  authorId: string;              // 伙伴 id（或 "human"）
  authorKind: "human" | "bot";
  threadId: string;              // 真身所在子会话 ← 关键：可回溯
  itemId: string;                // 子会话里的 item
  kind: "text" | "card";
  card?: CardPayload;            // 卡片时才带
  replyTo?: string;              // @ 路由出来的因果链
  at: number;
};

// 账本（早建，否则补不回来）
type LedgerRow = {
  agentId: string;
  source: string;                // "human" | "automation" | 上级 agentId
  groupId: string;
  tokens: number;
  msgId: string;
};
```

**为什么消息投影要带 `threadId + itemId`**：群视图只做聚合，点开仍落到原子会话——这样记忆归属、压缩、上下文进度全部沿用现有机制，不需要给"群"再写一套。

## 4 五条设计决策

### ① 群是聚合视图，不是消息容器
- 群内发消息 → 落到**目标伙伴的子会话**，同时写一条投影到群索引。
- 群视图 = 订阅这些子会话的事件流，按 `at` 合并排序。
- 好处：上下文隔离（每个伙伴自己的窗口）、记忆归属不变、压缩互不影响。
- 代价：群内"十个人同时说话"的观感需要**前端合并 + 去重**，不能靠后端一个流。

### ② @ 路由复用现有提及模型，只加一个 kind
- 现有 `mentionKindAllowed` 已支持 kind 开关联动；加 `kind: "partner"`（对应飞书的 `single_bot`）。
- 路由 = `@谁 → 派给谁的子会话`；未 @ 的伙伴**不参与**（除 `respondToBotMentionOnly=false` 时的广播场景）。
- 广播用**现有 dispatch 的复用闸**（同一目标复用子会话），不新开线程。

### ③ 卡片分两期，先不碰交互
- **P2**：只读卡片（`text / markdown / hr / table / img / chart`）——覆盖"报表、对比、图表"这类 90% 的实际用法。
- **P3**：交互（`button` + 三动作）+ 按 `cardId` 流式刷新。
- ⛔ 一上来就做完整 schema（飞书实测 20+ 节点）会拖死进度，且大部分节点用不上。

### ④ 记忆 `origin` 必须早于群
- 现在记忆有分层、有 `dispatch.originThreadId`，但**没有"这条记忆来自哪次对话"**。
- 加 `origin: { groupId?, threadId, msgId, authorId }`——豆包实测的 `origin=群ID-人` 就是这个。
- ⛔ 顺序：**先 origin，再做群**。反了的话，群里的结论写进记忆后无法溯源，删都不敢删（豆包坑 2）。

### ⑤ 设备租约（P5，可推迟）
- 现有 `remote.ts` 是"手机 → 电脑"（电脑做服务端）。团队模式需要反过来：**"云端/应用 → 异地电脑"**（电脑做客户端出站长连）。
- 两者不冲突，但设备侧必须做**单设备串行租约**（豆包坑 1：N 个 agent 抢一只手）。
- 建议 P5 单独做，且第一版只支持"一台设备 + 排队"，不做多设备选择（豆包坑 3 明确说默认值必错）。

## 5 分阶段（按投入产出，不按依赖关系全做）

| 阶段 | 做什么 | 验收标准 | 估计 |
|---|---|---|---|
| **P0** | 群视图（聚合 N 个子会话消息）+ 成员表 + @ 路由 `kind:partner` | 主理人 @ 两个伙伴，两条回复按时间轴出现在同一个群视图里；点任一条能跳回它的子会话 | 2–3 天 |
| **P1** | 记忆 `origin` + 团队作用域 | 重启后能看到"这条记忆来自哪个群、哪次对话、谁写的"；`memory_write` 落 origin | 1–1.5 天 |
| **P2** | 只读卡片（text/table/chart/img） | 伙伴回复里能渲染一张对比表 + 一张图，样式与现有工具卡一致 | 2 天 |
| **P3** | 卡片交互（button + 三动作）+ 卡片级流式刷新 + 菜单树 | 点卡片按钮能触发对应伙伴的回调并原地更新同一张卡 | 2–3 天 |
| **P4** | 账本 `(agent, source)` + 群护栏（范围/禁外部/不响应 @所有人） | 7 天报表能按"人 / 下级伙伴 / 自动化"拆开；外部群拉不进 | 1–1.5 天 |
| **P5** | 设备出站长连 + 单设备租约 | 云端下发 `echo hi` 拿到输出；并发第二个任务被明确拒绝（不是静默排队） | 3–4 天 |

**P0+P1 是主轴**（约 4 天），做完就能对内演示"团队协作 + 结论可溯源"。

### 与两份报告的逐条对位（11-06 复核：用户「外部是什么、上下级看不懂、没有群记忆/群文件」）

复查两份逆向报告后确认：上一版有**三块是照词抄的空壳**，在我们这里没有对应语义 ⇒ 已删。

| 我做的 | 报告里是什么 | 判定 |
|---|---|---|
| 群护栏「允许外部成员加入」 | 飞书：跨租户**外部群**（`isCrossTenant`，逆向第 30 行）+ 外部共享机器人（第 96 行） | ❌ 空壳：本应用没有租户概念 |
| 群护栏「响应 @所有人」 | 飞书群 `@all` 消息类型 | ❌ 空壳：我们没有 @所有人 这个动作 |
| 群护栏「协作范围 project/dept/all」 | 豆包：协作范围 = **部门**（企业组织树） | ❌ 空壳：没有部门这一层 |

**报告里还有、我们仍未做的**（按报告的价值排序，别按我的顺序）：
1. **记忆 `origin` 溯源**（豆包第 78、321 行点名「记忆没有 origin 会烂」）—— 群记忆目前只有内容，没有"这条谁写的/从哪个群哪次对话来的"
2. **设备长连 + 单设备租约**（豆包第 ③ 节 / P5）
3. **飞书桥接**（P6 可选，见 §8）

已完成（11-06）：卡片消息 + `cardId` 原地流式（P2/P3）、成本账本 `(agent, 来源)`（P4）、机器人菜单两种形态（P3）、自动化定时（P4）。

**P0b 实测撞出来的三个 bug**（都已在同轮修掉，记在这里防复发）：
1. 「建群」从来没成功过 —— create 拿 `groupIssues` 当闸，而「还没有伙伴」是提示不是错误 ⇒ 任何新群都被拒。
   已拆成 `createBlockers`（结构性硬闸）/ `groupIssues`（含建议类）。
2. `--accent-text` 是**强调底上的前景色**（浅色主题 = #fff），拿来当文字色 = 白字隐身。
   文字/描边一律 `--accent`。
3. 派活失败不能写假消息 —— 错误走状态条，不进消息流。

**已知边界**：① 「专家团成员」类目标要用户先在顶栏「调度」打开专家团（既有权限模型，不绕过）；
② 回复**完成后**上屏，尚无逐 token 流式；③ 同一个人伙伴加进两个群会共用同一条子会话
（复用键是 `kind:targetKey`，要拆开得给群一条 anchor 会话，放 P1 一并做）。

## 6 五个坑（豆包实测反推，不是理论）

1. **设备串行化不能省**：一台设备「所有人可用」= N 个 agent 抢一只手。租约必须在 `finally` 释放，且连接要能自愈重连。
2. **记忆没有 `origin` 会烂**：多个伙伴往同一份记忆写，三天后没人知道某条结论出自哪个群哪次对话。
3. **多设备"选哪台"是伪需求的第一版**：默认值必错，先做单设备排队，别提前做选择 UI。
4. **执行端认证态与云端解耦**：设备登录态掉了，云端只拿到一个报错 ⇒ 必须把"需要人工介入"作为**独立任务状态**暴露，不能当普通失败重试。
5. **成本必须按 `(agent, source)` 记，且一开始就记**：事后补账本 = 重跑历史，做不到。

## 7 明确不做（边界）

- ⛔ 不做 DAG 编排引擎、不做向量库、不做微服务（豆包材料已论证：不需要）。
- ⛔ 不引入全局 store；群状态跟现有 `bag` 域走。
- ⛔ 不把多个 agent 塞进同一个引擎 thread（见 §0）。
- ⛔ 第一版不做：多设备选择、外部伙伴、跨租户、计费结算（只记账不收费）。
- ⛔ 不重写专家团：`expert-teams` 继续只负责"团队模板定义"，运行时全在新板块。

## 8 与飞书的关系（可选，不是前置）

两层解耦：
- **应用内群是主形态**：不依赖飞书，本地就能跑通 P0–P4。
- **飞书桥接是加分项**：消息结构已经按飞书的 `author / cardContent / action` 语义设计，将来接 `lark-im` 只需加一个"群 ↔ 飞书群"的映射层（进/出双向），**协议不用改**。

判定：**先自建群，桥接放 P6**。反过来做（先接飞书）会把协议约束和网络依赖引进 P0，拖慢主线。
⛔ 注意区分两件事：**复刻飞书群的形态**（P0–P4 要做，应用内自建）≠ **连飞书群**（P6 可选桥接）。

## 11 合成后的产品形态（用户视角）

```
侧栏
└── 团队
    └── 「智慧厨房」群            ← 点开是消息流（不是名单）
        ├── 群头：成员头像行（人 1 + 伙伴 3）+ 「@」按钮 + 菜单按钮
        ├── 消息流：
        │     [我]        把本周销量核对一下 @数据师
        │     [数据师 bot] （卡片：销量对比表 + 趋势图）
        │     [我]        按这个结论出个促销方案 @推广
        │     [推广 bot]  （文本 + 待确认按钮）
        └── 输入框：@ 伙伴选择器 · 伙伴菜单 · 发送
群设置
├── 伙伴：数据师 / 推广 / 客服（+ 添加、移除、静音）
├── 上下级：主理人 = 小智店长；数据师上级 = 小智店长
├── 护栏：范围=本项目 · 禁外部 · 不响应 @所有人
└── 账本：本周 3,240 次调用（人 41% / 数据师 33% / 自动化 26%）
```

**关键体验目标**：用户在群里 @ 一下就派活，回复以卡片回来，点开任一条能落到该伙伴的原子会话看全过程；一周后能查「这结论谁写的、花了多少」。

## 12 两条路线的取舍（回答"要不要真的连飞书"）

| | A. 应用内自建群（本方案） | B. 应用当飞书机器人 | C. 两者都做 |
|---|---|---|---|
| 用户在哪用 | 我们应用里 | 飞书里 | 两边都能 |
