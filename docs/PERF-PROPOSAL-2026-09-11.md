# 性能优化整改方案：整改前 / 整改后利弊

> 2026-09-11 起草。结论基于对本项目源码的实测核查，以及对 WorkBuddy `app.asar`（1144 个 JS）的拆解对照。

## 一、先纠正：上轮三项建议里有两项我们已经做了

| 建议项 | 实际现状 | 判定 |
|---|---|---|
| ① 流式合帧 | **已实现，且比参照方案更细**（`src/App.tsx` 的 `flushDeltas`） | ❌ 无需整改 |
| ② 引擎进程预热池 | **未做**，当前是单进程 + 必要时 kill 重启 | ✅ 唯一真缺口 |
| ③ 虚拟列表 overscan | **已用更合适的方案替代**：回合窗口化（`TURN_WINDOW = 40`）+ 轻量 resume | ❌ 无需照搬 |

### ① 流式合帧：我们做得比 WorkBuddy 更细

`App.tsx` 里 `pendingDeltaRef` + `requestAnimationFrame(flushDeltas)` 的合帧，三个细节是 WorkBuddy 没有的：

- **首 token / 停顿后的字立即可见**：距上次落盘 >24ms 就立即 flush，不等 rAF——否则肉眼就是「慢半拍、憋一段才冒出来」；
- **结构性事件后置**：`item/completed` 必须排在已缓冲 delta 之后，否则会「先落完成态、后补字」，表现为正文被覆盖或整段丢失；
- 一帧内多条 delta 合并成一次 `setThread`，只触发一次全树重渲染。

### ③ 时间线渲染：窗口化比 content-visibility 更贴本机

`App.tsx` 注释里已有论证：「这台机器是软件渲染（无 GPU），把几千个回合一次性挂进 React 是『切会话要等很久』的主因——**content-visibility 只省绘制，省不掉建元素与 Markdown 解析的成本**」。

因此对本项目而言，`content-visibility` 是无效的对照项（它只对 WorkBuddy 那种有声显卡的机器有用）。现状方案是：

- `TURN_WINDOW = 40`：首屏只渲染最近 40 个回合，更早的按需展开；
- `resumeThreadLight`：以 `excludeTurns:true` 取元数据，避免引擎全量水合几千回合——注释明确写着这是「切会话慢」的数据侧主因，渲染侧已窗口化。

## 二、唯一真缺口：引擎单进程 + 重启

`electron/codex-server.ts` 的 `restart()` 实现是：

```
kill 旧进程 → reject 所有 pending 请求 → spawn 新进程 → initialize
```

三个后果：

1. **正在跑的回合被杀**：`pending` 全部 reject，在跑的流式输出中断，需要 survive 逻辑救（App.tsx 里 `refreshThreads` + `resumeThread` 那些分支就是为这个服务的）；
2. **冷启动成本每次重新付**：900ms~数秒级（视机器上引擎启动快慢），且 spawn 要加载 toolchain env、nodefind restrictions；
3. **触发面广**：`App.tsx` 里「重启引擎」出现 **21 次**（登录 OpenAI 订阅、保存供应商、添加 MCP 连接器、改模型配置……）。也就是说这是个**高频动作**，不是偶发的。

## 三、三个方案与利弊

### 方案 A：热交接（推荐）—— 新旧引擎并存，滚动切换

做法：改配置时**不 kill 旧进程**；spawn 新引擎 → initialize 完成 → 新会话/新回合路由到新引擎 → 旧引擎在没有活跃回合后自行退出。

| | 内容 |
|---|---|
| **利** | 正在跑的回合不被杀（消除 survive 逻辑的前提，顺带简化 `App.tsx` 里那批恢复分支）；用户体感「切供应商不中断」；不必常驻多进程，内存与现在持平；改动集中在 `codex-server.ts`，风险可控 |
| **弊** | 存在短暂的「两个进程同时活着」窗口；需要一个路由层把会话绑定到具体进程；`（helpful）二者并存期间电池/CPU 略升 |
| **风险点** | 同一 `CODEX_HOME` 下两个进程并发写 rollout 的可能性——需确认引擎是否自己加锁；若没有，必须让旧进程只读（不接新回合） |

### 方案 B：进程池 + 预热（WorkBuddy 同款）

做法：按「供应商/配置」维度常驻一个引擎进程，提前 spawn 待命，切场景直接领取（WorkBuddy 实测把 3.7s 降到 1ms）。

| | 内容 |
|---|---|
| **利** | 切换零等待（毫秒级）；顺带彻底解决「换供应商要重启」；与下发的 `--model` 冷启 argv 问题天然配合 |
| **弊** | **内存随供应商数线性增长**（每个 codex app-server 进程不小）；池化管理是有状态复杂度——WorkBuddy 就踩过坑：把探活放在领取路径上同步 ping，Windows 上误杀健康进程，表现是「第一次慢、第二次快」（issue #75795）；多进程共享 `CODEX_HOME` 的 rollout 并发写是硬风险，需要先做 `CODEX_HOME` 隔离 + 会话归属表 |
| **适用前提** | 你真的频繁在多个供应商之间切。若一天切不了几次，B 的复杂度不值得 |

### 方案 C：维持现状，只补文档与提示

| | 内容 |
|---|---|
| **利** | 零开发成本、零风险；当前 survive 逻辑已经能让重启后自动 resume，用户不会丢消息 |
| **弊** | 「切供应商会打断正在跑的回合」这个体验损失长期存在；每次改配置仍要付冷启动成本 |

## 四、建议

**先做方案 A**。理由：收益（不打断回合）确定、改动面小（一个文件为主）、内存不涨、且消posing 掉了 App.tsx 里大量围绕重启的恢复分支——属于「改一个地方，多处变简单」。

方案 B 留作后续选项，且**只有在做完「rollout 并发写」的验证之后**才考虑。判断依据很简单：如果你一天之内切供应商不超过 2~3 次，B 的常驻成本大于收益。

## 五、验收方式（照 project 铁律）

- 纯逻辑抽到 `src/lib/*.mjs`，在 `scripts/check-preflight.mjs` 里加行为断言（路由层：会话 → 进程绑定、旧进程只读）；
- 补 e2e 场景：断言「改供应商并保存后，正在流式输出的回合不中断 / 不出现 `Codex app-server restarted` reject」；
- 新断言当场反证一次（把热交接改回 kill 重启，确认断言会红）；
- `npm run verify` 退出码 0 才算完成。

## 附录：多进程前提验证（2026-09-12 05:05 实验定案，脚本 .e2e-artifacts/multiproc-probe.mjs）

**实验**：两个裸 codex.exe app-server 进程共享同一 CODEX_HOME，并发 thread/start + 各 3 个 turn/start（共 6 回合并发）。

**结果**：
- ✅ 全部成功，rollout 按会话分文件（2 个 .jsonl 各自独立），**文件级并发写不互损**——方案 A/B 的头号风险（rollout 并发写冲突）解除
- ⚠️ thread/list 各进程只看到自己的会话（互不可见）→ 多进程架构下「会话列表」必须在宿主层聚合（遍历各进程 thread/list 合并）
- ⚠️ 每进程一份内存/CPU 开销；config.toml 并发写风险仍在（引擎某些操作会写它），需在设计中规避（配置变更走 flush 重建，运行期只读）

**「每会话一进程」的完整工程量（WorkBuddy 式）**：
1. CodexServer → 引擎管理器：会话→进程路由表 + 进程生命周期（prewarm/activate/kill）
2. 全局 RPC 聚合：thread/list、搜索、归档等跨进程合并（main.ts 数百处 server.* 调用按 threadId 分派或走主实例）
3. 事件流路由：notification 带 threadId，按归属进程回传渲染层（事件本身已带 threadId ✓）
4. 渲染层零改动可行（IPC 契约不变）
5. 工期：数天级重构，非一晚可安全完成；且需与「切换会话」改动的并行任务协调落点

**建议路径**：先上「方案 A 热交接」（单引擎多会话不变，配置切换不断回合，1 晚可完成）；「每会话一进程」作为二期，待切换会话改动合流后动工。
