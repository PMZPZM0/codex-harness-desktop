# 命令 → 意图映射：WorkBuddy 的做法分析，以及本项目的落点

> 2026-09-24。**证据口径先说清**：WorkBuddy 是闭源宿主，以下结论来自 ① 其界面实际行为（工具卡文案、
> 折叠芯片、编辑卡的 `+N -M`）；② 本项目在同一类引擎（Codex app-server）上跑真回合拿到的 item
> 载荷（rollout 逐条 dump）。**凡属推断的地方都标了「推断」**，不做源码级断言。

## 1. 证据：同一条命令，两种呈现

真机采样（本机 e2e profile，一次真实回合）：

```
CommandExecution :: C:\…\pwsh.exe,-Command,Get-Content -LiteralPath '…\.workbuddy\skills\humanizer\SKILL.md'
```

同一份载荷，WorkBuddy 的界面呈现是「**使用技能 去 AI 味**」，本项目原先是
「已运行 `$ws='…'; "=== 结构 ==="; Get-Content …`」。差别不在数据，而在**映射层**。

## 2. WorkBuddy 的映射机制（四层，逐层可验证）

| 层 | 输入 | 输出 | 可观测证据 |
|---|---|---|---|
| ① 采集 | 引擎 item（`CommandExecution` / `FileChange` / MCP 调用 …） | 归一化事件 | 工具卡的数据与 rollout 逐字一致 |
| ② **分类** | 命令/工具字面 | 意图档位（运行 / 查看 / 定位 / 编辑 / 使用技能 …） | 同类命令稳定同文案，不同类立刻分档 |
| ③ **提炼** | 命令正文、入参、diff | 展示对象（文件名 / 用途标签 / `+N -M`） | 长脚本被压成「用途 · 目标」；编辑卡带真实行数 |
| ④ 渲染 | 上面三类 | 卡片表头 / 折叠芯片摘要 | 同一事件在「明细卡」「芯片」两处口径一致 |

关键机制（推断，但被行为强约束）：
- **数据来源是载荷本身，不是静态注册表**。证据：同一命令在不同参数下文案随之变化（`Get-Content A`
  与 `Get-Content B` 显示不同目标）——静态注册表做不到这一点，只有"从字面提炼"能做到。
- **映射是纯函数、在渲染时算**（无持久化）。证据：切会话、重播历史时文案一致，且旧的会话也按新
  规则显示（说明没有把结果写进历史）。
- **两级降级**：提炼得出目标 → 显示「用途 · 目标」；提炼不出 → 退回命令原文（而不是显示空或假标签）。
- **量化状态来自 diff 载荷**：`编辑 xxx.mjs +39 -2` 的行数只有解析 unified diff 才能得到，
  说明它在展示层真的读了 `FileChange.changes`。

## 3. 本项目的实现（已落地，守卫【127】/【2】）

| 能力 | 实现 | 落点 |
|---|---|---|
| 命令二级意图 | `commandIntentOf`（词法判定：modify > search > read > command） | `src/lib/command-display.mjs` |
| 用途提炼 | `commandPurpose`（先丢变量赋值段，再取含中文的输出标签） | 同上 |
| 目标提炼 | `commandTarget`（剥壳启动器 → 路径归一 → 保尾截断） | 同上 |
| **技能归属** | `skillOfItem`（工具特征 + `…/skills/<名>/` 路径兜底 + 本地技能清单翻译） | `src/lib/tool-display.mjs` |
| 行级真实状态 | `diffStats` 解析 unified diff → `+N -M` | `src/lib/diff-stats.ts` |
| 渲染 | 命令行卡 `TerminalPanel` / 工具卡 `ItemView` / 折叠芯片 `turn-fold` 三处同源 | `src/features/…` |

⛔ 落地时踩到的两个坑（都写进了守卫）：
1. **同一条事实必须在所有落点共用同一函数**（卡片与芯片各写一套 ⇒ 必然跑偏）；
2. **"技能用量最大的形态是一条命令"** —— 只接工具卡会漏掉绝大多数（真回合实测）。

## 4. 可借鉴之处

1. **载荷即真相源**：文案从载荷算，不引入第二份注册表 ⇒ 引擎升级/新工具自动有兜底表现。
2. **两级降级而不是二选一**：提炼失败退回原文，绝不显示空或猜的标签。
3. **同一事实一个函数**：分类/提炼做成纯函数，被卡片、芯片、导出多处复用（本项目已按此对齐）。
4. **量化优先**：能算出数字就上数字（`+N -M`），比形容词（「修改了文件」）信息密度高一个量级。

## 5. 局限（对重度使用者的诚实清单）

1. **无"计划态"**：只能描述**已发生**的调用，无法显示"这条命令将要做什么"（要那个得读模型计划）。
2. **词法判定的边界**：`commandIntentOf` 是启发式 —— 又读又写的复合脚本、动态生成的命令字符串会归错档；
   能保证的是"认不出归 command"，不会硬猜。
3. **技能只有"使用痕迹"才可见**：若技能内容已进上下文、模型既没读文件也没产生工具调用，引擎无 item
   ⇒ 界面无从显示（这是引擎事实，不是映射层能补的）。
4. **跨进程/委派会话的调用**由主进程直接发起，渲染层这套映射够不到。
5. **国际化词表**：用途提炼依赖中文输出标签（脚本作者写的 `"=== 结构 ==="`），英文标签或纯符号脚本会退回原文。
