# 审查流程完整要点

> 收敛自 alibaba/open-code-review 的任务模板与各阶段提示词（Apache-2.0）。
> SKILL.md 给的是六步主干；本文件补充**大改动**才用得到的分组、预判、预算、定位修复四件事。

## 一、整体流水线（一次审查经历什么）

```
取改动 → [分组] → [风险预判] → 逐组正式审查（可多轮）→ 去误报过滤 → [定位修复] → 报告
```

方括号里的步骤**按条件触发**，不是每次都有：

| 阶段 | 触发条件 | 作用 |
|---|---|---|
| 分组（grouping） | 变更文件数 ≥ **4** | 把文件按语义聚类，**同组一起审**（同模块/生产者-消费者/同资源的 i18n 变体/同目录同职责）。每组最多 **10** 个文件；**每个文件必须恰好落进一组** |
| 风险预判（plan） | 单个最大改动文件 ≥ **50** 行，**或**同组 2 个以上文件合计 ≥ **100** 行 | 先出「变更意图摘要 + 风险点清单（带严重度）+ 取证计划」，再正式审 |
| 多轮复审 | 按审查强度：low=**1** 轮 / medium=**2** 轮 / high=**3** 轮 | 后续轮次针对前轮未确认/新发现继续追 |
| 定位修复（re-location） | 意见引用的代码片段在文件里**匹配不上**（行号为 0） | 从 diff 里**原样**摘出意见真正指向的那段，重新定位 |

## 二、分组细则（文件 ≥4 个时）

- 同组的典型特征：同一模块/功能；有生产者-消费者关系（接口与实现）；同资源的语言/配置变体（`message_zh.properties` 与 `message_en.properties`）；同目录且服务同一件事。
- 硬约束：**每个文件恰好一组**；单文件成组是允许的（确实无关时）；**每组上限 10 个**。
- 分组的意义：让同一个上下文只读一次，且**跨文件的不一致能被看见**（接口改了实现没改、常量改了引用没改）。

## 三、风险预判细则（大改动时）

输出一份**结构化计划**，每部分只承载一件事：

```
Summary: （这段改动要干什么、范围多大）

Issues

1. [high|medium|low] （问题位置 + 问题性质 + 潜在影响，三要素齐全）
   → （要读的文件 / 要检索的符号）—（调用它的目的：证实还是排除这个风险）
2. [medium] ...
```

规则：
- **只分析新增和修改的代码**，忽略删除的代码。
- 问题按严重度**降序**编号。
- **工具只用于描述取证意图，不要真去执行**（这一步是规划，不是审查）。
- 严重度：`high` = 可能导致安全漏洞/数据丢失/系统崩溃/关键功能失效；`medium` = 影响性能、可维护性、或潜在边界问题；`low` = 风格、可读性、非关键最佳实践。
- **没有问题就写 `(none)`，不要为了填满列表而编问题。**

## 四、预算与规模控制

一次审查的硬约束（超出会静默截断或跳过，必须知道）：

| 指标 | 值 | 含义 |
|---|---|---|
| 单组提示词预算 | **200000** tokens（全文件扫描用 58888） | 整个会话上下文被压缩到这个预算内 |
| 单轮工具调用上限 | **100** 次 | 取上下文不能无限查 |
| 模型输出上限 | **16384** tokens | 单次回复的长度天花板 |
| 单文件 diff 占比 | 超过预算的 **~80%** | 该文件**在调模型前就被跳过** |

**实践含义**：改动特别大的文件，要么拆开看，要么明说"该文件超出预算已跳过"。**不许假装看过。**

## 五、定位修复细则（行号拿不到时）

当一条意见引用的代码片段在文件里匹配不上（`start_line`/`end_line` 落到 0）：

1. **从 diff 里原样摘**出意见真正指向的那段代码 —— **不要改写、不要重排、不要补充**。
2. 摘的时候**去掉 diff 标记**（行首的 `+`、`-`、空格）。
3. **只摘与问题直接相关的最小连续区间**，不要带上下文。
4. 有多个不相干位置时，只取**最相关的那个**。
5. 用这段重新在文件里定位，拿到真实行号。

**关键纪律**：定位失败**不等于**这条意见无效。先修复定位，再决定保留与否——**绝不可以因为定位失败就把意见丢掉**。

## 六、上下文压缩的纪律

审查会话变长时会压缩历史。压缩时**必须保住**这几类信息（丢了会导致后续判断失准）：

- 本次审查的范围与模式（workspace / range / commit）
- 已确认的发现（**避免重复报同一个问题**）
- 已排除的假设（避免反复回到同一个错误结论）
- 尚未审完的文件清单（避免漏审）

## 七、强度档位的选择建议

| 档位 | 轮次 | 适合 |
|---|---|---|
| low | 1 | 快速过一遍、改动很小、只想抓明显问题 |
| medium（默认） | 2 | 日常提交审查 |
| high | 3 | 发版前、核心链路改动、安全敏感代码 |

轮次多不等于更好——**低质量的意见重复三轮仍然是低质量**。宁可一轮做扎实（上下文读全 + 自审过一遍）。
