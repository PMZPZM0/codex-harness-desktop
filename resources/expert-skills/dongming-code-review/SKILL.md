# 洞明代码审查

审查的价值**不在挑出多少问题，而在挑出的每一个都站得住**。误报比漏报更伤信任：一条说不清复现路径的"疑似问题"会让整份报告被丢弃。

本技能包把审查拆成**六步闭环**。每一步都有明确产物，不要跳步。

---

## 第 1 步：确定审查范围（必须给出可复核的范围）

按用户意图选一种模式，**先确认范围再开审**：

| 用户说 | 范围 | 取改动的方式 |
|---|---|---|
| "审查我的改动" / 没说范围 | workspace | `git status --porcelain`；已跟踪 `git diff HEAD -- <path>`；未跟踪文件**直接整file读**（全是新代码） |
| "审查 PR / 分支" | range | 先 `git merge-base <base> <to>` 拿合并基点，再 `git diff <mergeBase>..<to> -- <path>` |
| "审查提交 xxx" | commit | `git show <commit> -- <path>` |
| "审查整个项目" | full-scan | 逐目录通读，**不限于 diff**（见「全文件扫描」） |

**范围产出**：一份文件清单（路径 + 新增/删除行数）。这是后面「覆盖纪律」的核对基准。

> ⛔ **未跟踪文件是重灾区**：workspace 模式下 `git diff` 看不到它们，但它们全是新代码。必须 `git status` 找出 `??` 的文件并逐个通读。

---

## 第 2 步：按语言取规则

读 `references/rule-map.md`，按文件路径匹配出它的**规则文档**（`references/rules/<语言>.md`）并读取。

- 匹配不到就退回通用规则 `references/rules/default.md`（正确性/安全/性能/可维护性/测试五个维度）。
- **一个文件只用一个规则集**（取第一条命中的）。
- 同语言的多个文件共享同一份规则，读一次即可，不要重复读。

规则文档是**审查清单**，不是让你逐条打勾——按改动性质挑相关的维度重点看。

---

## 第 3 步：读上下文（这一步是分水岭）

**只看 diff 是误报的头号来源**：你看不到调用方、数据来源、既有约束，于是把「上游已经保证过的前提」当成缺陷。

对每一处可疑改动，下结论前补齐上下文：

1. **读被改文件的完整内容**（不只 diff 片段）——文件的既有约定（错误处理风格、并发模型、分层）是你判断"这是不是问题"的基准。
2. **追调用方**：改了函数签名/返回语义/异常行为 → 检索调用点逐个核对。
3. **追被调用方**：改动依赖的函数，它的契约（是否可能返回空、是否线程安全、失败时留下什么状态）。
4. **看同批次其他文件**：一个改动常拆在多个文件里（接口 + 实现 + 调用点 + 测试），只看其中一个会得出错误结论。
5. **看测试**：关键路径有覆盖吗？改动是否让既有测试失效？

⛔ **禁止仅凭名字或 import 推断**：并发调用、攻击者可控、资源所有权、错误契约 —— 这些必须由代码或调用点证明。

⛔ **拿不到上下文就说"缺上下文，无法判定"**，不要猜。（上下文工具只用于取证；意见只能落在审查范围内的文件上。）

---

## 第 4 步：逐文件审查 + 覆盖纪律

把第 1 步的文件清单当**待办列表**，逐个过：

- 每个文件以 `(路径, 状态)` 为身份标识（workspace 模式下同一路径可能出现两次：先暂存删除、又新建未跟踪 —— 两个都要单独审）。
- 每个文件结尾必须是 **已审** 或 **明确跳过 + 具体原因**（如「纯生成代码」「diff 超过预算」「二进制」）。
- **不要在找到第一个高severity问题后就停下**。同文件继续看完，再进下一个。
- 大改动按「共享规则 + diff 规模」分批，每批读完再下一批。

**审查对象的边界（严格）**：
- ✅ 重点看**新增和修改**的代码。
- ⛔ 不评论正确代码、不评论未改动的代码。
- ⛔ 不评论被删除的代码（删除行只是参考上下文）。
- ✅ **鼓励跨文件发现**（同组文件间的不一致、漏改、契约破坏）——但意见必须落在清单内的文件上，不得指向范围外的文件。
- ⛔ 不评论非功能性元素（代码注释文字、`@Generated` 之类工具生成的标记），除非用户明确要求。

---

## 第 5 步：去误报自审（本技能包的核心）

**每条候选意见落笔前，套用 `references/false-positive-filter.md`。** 该文件是整套方法论的精华，核心规则：

> **默认全部放行。只有 diff 能\*证明\*它是错的，才删。**
>
> 两类错误的代价**不对等**：留一条错意见 = 审阅者浪费几秒注意力；删一条对意见 = 悄悄毁掉一个真实发现，它永远不会被任何人看到。

**自审四问**（过不了就删或降级为"疑似"）：
1. **前提成立吗**？这个变量真可能为空吗（上游有没有保证）？这条路径真会被走到吗？
2. **能复现吗**？说得出"什么输入/什么时序会触发"吗？说不出 = 疑似，不是缺陷。
3. **我看漏了吗**？读完整文件与调用方了吗？会不会项目在这里有显式约定？
4. **改法比现状更好吗**？会不会引入新问题（加锁导致死锁、加校验拒掉合法输入）？

**同时不要重复工具能查的东西**：编译器、类型检查器、lint、`go vet`、staticcheck、`gofmt` 已能可靠发现的问题，除非 diff 里有它们表达不出的**用户可见后果**，否则不要报。

**风格/格式/命名类意见**：只要陈述属实就保留（价值低不等于错），但**必须与缺陷分开列**，不得混进缺陷里充数。

---

## 第 6 步：定级与输出

### 每条意见的字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `path` | 是 | 相对仓库根的路径 |
| `content` | 是 | 问题描述（说清**位置 / 性质 / 影响**三要素） |
| `start_line` / `end_line` | 建议 | 新文件中的行号；拿不到就写 0 并说明 |
| `category` | 是 | `bug` / `security` / `performance` / `maintainability` / `test` / `style` / `documentation` / `other` |
| `severity` | 是 | `critical` / `high` / `medium` / `low` |
| `suggestion` | 可选 | 具体改法（给可执行方案，不写"建议优化"这种空话） |

### 严重度定义

- **critical** —— 可能导致数据损坏/丢失、安全漏洞、系统崩溃、关键功能失效。**必须改完再合并**。
- **high** —— 明确的逻辑缺陷、并发/资源问题、破坏兼容的行为变更。**应该在合并前改**。
- **medium** —— 性能隐患、错误处理缺口、边界遗漏、可维护性硬伤。**可排期修**。
- **low** —— 风格、命名、微小的可读性问题。**只在确实有价值时才报**；真假难辨的直接丢弃（静默丢弃，不要列举）。

### 输出模板

```markdown
## 代码审查结果

**审查范围**：<workspace / range <base>..<head> / commit <hash> / full-scan>
**已审文件**：N / M（跳过 K：逐个列出路径与原因）
**发现问题**：X critical · Y high · Z medium

### Critical
- **`path/to/file.ts:42`** [`bug`] — 一句话说清问题
  > 依据：什么输入/时序会触发，后果是什么
  > 修法：具体怎么改

### High
（同上格式）

### Medium
（同上格式）

### 建议（非缺陷）
- `path/to/file.ts:88` [`style`] — 一句话

### 结论
可以合并 / 改完上面 N 条再合并 / 需要重新设计（架构层面有问题时直说并给理由）
```

**收尾必须交代覆盖情况**：审了几个文件、跳过哪些及原因、哪里缺上下文导致无法判定。**不许静默漏文件。**

### 两个输出细节

- **行号定位失败**（`start_line` 与 `end_line` 都是 0）时：读该文件、按意见内容里的上下文找到真实位置，再落行号；**不要因为定位失败就丢掉这条意见**。
- **报告要能逐条处理**：一条意见对应一处代码，不要把多个问题塞进一段话。

## 可选：大改动的风险预判（plan）阶段

改动规模大（单文件改动 ≥50 行，或一组文件合计 ≥100 行）时，**先做一轮风险预判再正式审**：

1. 通读 diff，写出**变更意图摘要**（这段改动要干什么）。
2. 列出**风险点**，每个标 high/medium/low：问题位置 + 问题性质 + 潜在影响。
3. 每个风险点写出行**取证计划**（要读哪个文件/检索什么符号，去证实或排除它）。
4. 按严重度降序排。

这一步的意义：把"顺手看一遍"变成"带着假设去验证"，避免大改动里漏掉深层问题。

## 可选：全文件扫描（full-scan）

审查目标不是 diff（接手陌生代码库、或 diff 无意义）时：
- 按目录逐层通读，**每个文件都套第 2 步的规则文档**。
- 关注点是**代码本身的质量与风险**，不是"改了什么"。
- 规模大时同样分批，并明确报告覆盖到哪、还剩哪些没看。
